## 全体の構成（案）

- 同期は本体（`index.html`）で行う。新しいファイル：`js/sync.js`（同期の本体）、`js/sync-gdrive.js`（Googleドライブとのやり取り）
- 各アプリのDBは本体と同じオリジンなので、本体から開ける
- 保存先ごとの違いは「一覧・読む・書く・消す」の4操作に閉じ込める。OneDriveに対応するときは`js/sync-onedrive.js`を足すだけにする
- 端末内に同期の管理用DB `sideops_sync` を新設する。中身は端末ID、前回同期した時点の状態（レコードごとの指紋と版）、競合で負けた版の控え、同期の記録

### IndexedDB実装パターンとの関係（唯一の例外）

`platform/claude_IndexedDB実装パターン_仕様書.md`は「DB名は機能ごとに完全に独立させる（他アプリのデータへアクセスする手段自体を作らない）」としている。同期の本体はこの原則の**唯一の例外**として、すべてのDBを読み書きする。歯止めは次のとおり。

- 触れるのは、同期対象の一覧（許可リスト）にあるDBだけ
- 端末にまだ存在しないDBを`indexedDB.open(名前)`で開かない。版を指定せずに開くと空のDBが版1で作られ、後からアプリが開いたときに初期化（`onupgradeneeded`）が走らず、アプリが壊れる。存在の確認には`indexedDB.databases()`を使う
- アプリ側の版上げを妨げないよう、接続は使い終わったらすぐ閉じる。`onversionchange`を受けたら即座に閉じる

## クラウド上の形式（案・v1/v2共通）

### 置き場所

Googleドライブの`appDataFolder`（このアプリ専用の隠し領域）を使う。

- SIDE-OPSは利用者のほかのファイルに触れない。逆に、ドライブの画面からもこの領域は見えない
- 権限は`drive.appdata`だけを求める

### ファイルの構成

```
manifest.json      … 形式の版・暗号化の設定（ソルト・反復回数）・包んだデータ鍵・鍵の確認用データ（ここだけ暗号化しない）
device_<端末>.enc  … 端末の情報（端末名・最終同期時刻・アプリの版）
db_<端末>_<DB>.enc … その端末が持っている、そのDBの全レコード（削除の印を含む）
blob_<識別子>.enc  … 画像などのバイナリ。1点1ファイル
```

- ドライブはフォルダをたどるより名前で探す方が手数が少ないので、平らに並べて名前で区別する
- ファイル名には、中身を推測させる情報（DB名・端末名）を入れない。`<端末>` `<DB>` `<識別子>`は鍵付きハッシュ（HMAC）で作り、本当の名前は暗号化した中身に書く

### 各端末は自分のファイルにだけ書く

- 端末は、自分の端末IDのファイルにだけ書き込む。ほかの端末のファイルは読むだけ
- 2台が同じファイルに書くことがないので、保存先側の「上書き前の版確認」に頼らずに済む。Googleドライブがこの確認に対応しているかは、公式資料で確認できなかった
- 読むときは全端末のファイルを集め、レコード単位で合流させる
- 使わなくなった端末（機種変更など）のファイルは、設定画面から消せるようにする

### DBファイルの中身（暗号化する前）

```json
{
  "format": "sideops-sync-db",
  "formatVersion": 1,
  "db": "sideops_memo",
  "dbVersion": 1,
  "schema": {
    "entries":  { "keyPath": "id",  "indexes": [{ "name": "…", "keyPath": "…", "unique": false }] },
    "settings": { "keyPath": "key", "indexes": [] }
  },
  "appBuild": "2026-10-05",
  "device": "端末ID",
  "writtenAt": "2026-10-05T12:00:00.000Z",
  "stores": {
    "entries": [
      { "key": "m_…", "ver": "1759650000000-0000-端末ID", "value": { "…": "レコードそのまま" } },
      { "key": "m_…", "ver": "1759650000123-0000-端末ID", "deleted": true }
    ]
  }
}
```

- `schema`には、ストア名・キー・索引を記録する。アプリをまだ一度も開いていない端末でも、正しい形のDBを作れるようにするため。v2がデータの構造を知るためにも使う
- `value`はレコードをそのまま入れる。ただし、バイナリは参照に置き換える。
  - Blob → `{ "$sideopsBlob": "<識別子>", "type": "image/png", "size": 12345 }`
  - 画像のdata URL（壁紙・SCAFFOLD） → `{ "$sideopsDataUrl": "<識別子>", "type": "image/jpeg" }`。端末に戻すときは元のdata URLの文字列に戻す
- バイナリは値をたどって自動で見つけるので、アプリごとの設定は要らない。data URLとみなすのは、全体がdata URLの形で、一定以上の長さがある文字列だけにする（メモ本文などの誤判定を防ぐ）

### 画像（バイナリ）

- 1点1ファイルにする。名前は中身から作る鍵付きハッシュにする
- 同じ画像は1回しか送らず、変わっていない画像は送り直さない
- 名前が同じなら中身も同じなので、ファイルの書き換えが起きない。つまり、画像のファイルでは競合が起きない
- どこからも参照されなくなった画像は、すぐには消さず、一定期間（例：30日）たってから片付ける。ほかの端末がまだ参照している可能性があるため

### 圧縮

テキスト（DBファイル）は、暗号化の前にgzipで圧縮する（ブラウザ標準の`CompressionStream`を使う）。画像はもともと圧縮されているので、そのまま送る。

## 暗号化（案）

鍵を2段に分ける「封筒暗号化（envelope encryption）」という定番の方式を使う。

- **データ鍵**：ランダムに作るAES-256-GCMの鍵。すべてのファイルをこの鍵で暗号化する
- **データ鍵を包む鍵**：パスフレーズからPBKDF2-SHA256で作る（反復回数60万回。OWASPの推奨値）。データ鍵をこの鍵で包み、manifestに置く
- パスフレーズを変えても、データ鍵を包み直すだけで済む。全ファイルを暗号化し直す必要はない

細かい決まりは次のとおり。

- 暗号化のたびに、ランダムな初期化ベクトル（IV、96bit）を作る。同じIVは使い回さない
- 付加データ（AAD）に「ファイルの種類・DB・端末」を入れる。別の端末や別のDBのファイルとすり替えられたら検知できる
- ブラウザ標準のWeb Cryptoだけで作れる。Dart（v2）でも同じ方式を使える。独自の暗号は作らない

パスフレーズの歯止め：

- 最低の文字数を決める（例：12文字以上）。設定するときは2回入力して照合する
- 忘れた場合、クラウドのデータは誰にも復元できない。ただし、どれか1台の端末にデータが残っていれば、「同期をやり直す（新しいパスフレーズでクラウドを作り直す）」で復旧できる。致命的になるのは全端末を失った場合だけなので、書き出しによるバックアップと併用する

**データ鍵は端末に覚えさせる（2026-10-05決定）**

- 取り出せない形の鍵（non-extractableなCryptoKey）として`sideops_sync`に保存する。パスフレーズを入力するのは、その端末で同期を始めるときの1回だけ
- 理由：端末内には元から平文のデータがあるので、鍵だけを守っても効果が薄い
- 「この端末を忘れる」で、覚えた鍵と同期の状態を消せるようにする（端末内のアプリのデータは消さない）

**端末をなくしたときの歯止め**

- なくした端末は鍵（データ鍵そのもの）を覚えている。そのため、パスフレーズを変えるだけ（データ鍵を包み直すだけ）では、その端末を締め出せない
- 残った端末から「データ鍵を作り直す」を実行できるようにする。新しいデータ鍵で全ファイルを暗号化し直し、なくした端末のファイルも消す。パスフレーズの変更とは別のボタンにする
- あわせて、Googleアカウントの設定画面から、なくした端末のログインを取り消す（利用者の操作。手順を画面に案内する）

## 認証（Google）

- 求める権限は`drive.appdata`だけ。Googleの分類では「機密でない」権限で、厳しい審査は要らない
- アクセストークンは約1時間で切れる。メモリにだけ置き、IndexedDBには保存しない。切れたら取り直す
- SIDE-OPSは誰でも開けるページだが、Google側のアプリ登録を「テスト中」のままにして、テストユーザーを自分だけにする。他人がSIDE-OPSを開いてもログインできない（歯止め）。SIDE-OPSを配布する段階になったら見直す

### ログイン方式（2026-10-05決定：A）

| 方式 | 内容 | 長所 | 短所 |
|---|---|---|---|
| A. 公式ライブラリ（GIS） | Googleが推奨するブラウザ向けライブラリ（`accounts.google.com/gsi/client`）を読み込む | 公式に推奨され、保守されている | Googleのサーバーから読み込んだスクリプトが、SIDE-OPSと同じオリジンで動く。理屈の上では全アプリのデータと鍵に手が届く。RECONの「顧客データを扱うページに外部サーバーのスクリプトを入れない」方針と衝突する |
| B. ライブラリを使わず直接 | Googleのログイン画面へ移り、戻ってきたURLからトークンを受け取る（implicit flow） | 外部のスクリプトが一切入らない | Googleが「安全でない」「旧方式の互換と調査のためだけに提供している」と明記している。将来止められる可能性がある |
| C. 認可コード＋PKCE | 現在の一般的な推奨方式 | ― | Googleの「ウェブアプリケーション」の種類では、PKCEを使ってもクライアントシークレットが必須。サーバーのないSIDE-OPSでは秘密を守れない。**不採用** |
| D. 別のオリジンでログインだけ行う | ログイン専用の小さなページを別のオリジン（例：無料で作れるGitHub組織のPages）に置き、そこでGISを使ってトークンを受け取り、SIDE-OPSへ`postMessage`で渡す | Googleのスクリプトが、SIDE-OPSのオリジンでは一切動かない | GitHub組織とリポジトリが1つずつ増える。ログイン時にポップアップが2段になる |

**決定：A**。Googleのスクリプトを受け入れる。RECONの「顧客データを扱うページに外部サーバーのスクリプトを入れない」方針は、RECONのページ自体については今後も守る。顧客データを含む全データを送るのは本体ページになるため、本体ページについてはこの方針の例外とする。

採用の条件：

- GISはリポジトリに同梱できず、毎回Googleのサーバーから読み込む。読み込んだスクリプトはSIDE-OPS自身のコードと同じ権限で動く（ログインだけに閉じ込める仕組みはない）。これを承知のうえで採用する
- 読み込むのは本体ページだけ、それも同期を有効にしている間だけにする。同期を使わない端末では一切読み込まない
- 本体ページにCSP（読み込み元の許可リスト）を設け、スクリプトは自前とGoogleのログイン用だけに絞る。XSS対策としても効く
  - 本体ページにはインラインのスクリプトがない（2026-10-05確認）ので、`script-src`は絞れる
  - LOGパネルは利用者が設定したURLから取得するため、`connect-src`は取得先を事前に列挙できない。どこまで絞るかは実装時に決める
  - GISが必要とする読み込み先（ポップアップ・iframe等）は実装時に確認して許可リストを作る

## 同期のタイミング（案）

- **取り込み（クラウド→端末）**：起動したとき、タブが再び表示されたとき（`visibilitychange`）、手動のボタン
- **送り出し（端末→クラウド）**：
  - 変更があってから一定時間（例：30秒）操作がないとき
  - タブが隠れたとき。スマホでは最後まで終わらないことがあるので、できる範囲で行う
  - 手動のボタン
- **変更の検知**：
  - 各アプリは、保存のたびに本体へ「変更あり」と知らせる。テーマブリッジと同じ`postMessage`の仕組みを逆向きに使い、共通スクリプトに関数を1つ足す
  - 知らせが漏れても、起動時と送り出しの前に全DBを前回同期時点と比べ直すので、取りこぼさない
- **複数のタブ**：同じ端末で複数のタブが開いていても、同期を動かすのは1つだけにする（ブラウザ標準のWeb Locks APIで排他する）
- **基本の使い方**：端末を同時に使わないので、別の端末に移る前に「今すぐ同期」を押すのを基本にし、自動同期はその保険とする

## 変更の判定と競合（案）

### 3方向比較

前回同期した時点の状態（各レコードの指紋＝内容のハッシュと版）を`sideops_sync`に控え、今の状態と比べる。Unisonなどの同期ツールで使われている定番の方式。

- 前回はあったが今はない → 削除された → 削除の印を作る。**アプリ側の削除処理は変えなくてよい**
- 指紋が変わった → 更新された → 新しい版を付ける

### 版の付け方

- 端末の時計の時刻に、「今まで見た中で最大の版より必ず大きくする」補正をかける（Lamport時計の考え方）
- 時計が遅れている端末でも、同期した後の編集は必ず新しいと判定される
- 版は同期の側で付けるので、アプリごとの`updatedAt`の有無に左右されない（プロンプトギャラリー2種とDiscoticaには`updatedAt`がない）

### 合流と競合

- 合流するときは、レコードごとに版の大きい方を採用する
- 両方の端末で同じレコードを変えていた場合（競合）も、版の大きい方を採用する。負けた方は`sideops_sync`の「競合の控え」に一定期間（例：30日）残し、設定画面から確認・復元できるようにする
- 削除の印は、すべての端末が受け取ったと確認できるまで残す。その後、一定期間（例：90日）たってから片付ける

## 開いているアプリとの関係（案）

- Stageで開いているアプリのDBには、同期で書き込まない。アプリが閉じられたら反映する
- 待っている間は「ほかの端末の変更が届いています（アプリを閉じると反映します）」と表示する
- 端末を同時に使わない前提では、取り込みは主に起動直後（アプリを開く前）に起きる。この待ちが発生するのはまれ
- MINDFRAMEが持っている「保存直前の衝突確認」は、このときの2重の歯止めとして働く

## 同期の単位と対象

単位はDB（＝アプリ）ごと。設定画面で、DBごとに同期のオン・オフを切り替えられるようにする。

| DB | 初期値 | 理由・メモ |
|---|---|---|
| `sideops_launcher` | 同期する | |
| `sideops_settings` | 一部だけ同期する（2026-10-05決定） | 下の「本体の設定の分け方」を参照 |
| `sideops_log` | 同期しない（案） | 両方の端末で取得すると、取得先へのアクセスが倍になる。通知は取得先から取り直せる |
| `sideops_mindframe` | `views`以外を同期する（案） | `views`は表示位置・ズーム。画面の大きさが違うので端末ごとに持つ |
| `sideops_recon` | 同期する（2026-10-05決定） | 下の「RECONを同期するときの扱い」を参照 |
| その他のアプリ | 同期する | |

### 本体の設定の分け方（2026-10-05決定）

`sideops_settings`は、同じレコードの中に「同期する項目」と「端末ごとの項目」が混ざっているため、項目単位で分ける。

| レコード | 項目 | 扱い |
|---|---|---|
| `main` | `themeKey`・`customThemeTokens`・`eyedropperThemeTokens` | 同期する |
| `main` | `panelAlpha`（パネルの透過率）・`wallpaperValue`（選んでいる壁紙） | 端末ごと |
| `wallpaperUploads` | アップロードした壁紙画像（全体） | 端末ごと（同期しない） |

- ほかの端末から設定が届いたら、同期する項目だけを書き換え、端末ごとの項目はその端末の値を残す
- スポイトで作ったテーマ（`eyedropperThemeTokens`）は、作った端末の壁紙から生成した色の値をそのまま同期する。壁紙は端末ごとなので、ほかの端末では壁紙とテーマの元が一致しないことがあるが、色は保存した値のまま変わらない
- 新しい項目を`main`に足すときは、同期するか端末ごとかを必ず決め、この表に書き足す。決めていない項目は端末ごととして扱う（知らない項目を勝手に広げない）

### RECONを同期するときの扱い（2026-10-05決定）

- 購入者（第三者）の個人情報を含むが、暗号化して送る前提で同期に含める
- RECONのページ自体は、今後も通信を全面禁止にしたまま（CSPの`connect-src 'none'`）。データを読んで送るのは本体の同期機能
- 同期をオンにしたあと、RECONを初めて送る前に「顧客データを含みます。暗号化して送ります」と1回だけ確認する
- RECONの仕様書（`apps/claude_アプリ_RECON_仕様書.md`）の「端末ごとのデータ」の記述は、同期の実装時に書き換える

テーマブリッジの一時データ（sessionStorage）は対象外。

## アプリのバージョン差（案）

- 本体に「アプリの版」（日付の文字列）を持たせ、各端末のファイルに記録する
- 自分より新しい版の端末が書いたファイルを見つけたら、そのDBの取り込みと送り出しを止め、「SIDE-OPSを再読み込みして更新してください」と表示する。古い版が新しい項目を知らずに上書きし、その項目が消えるのを防ぐため
- DBの版（`DB_VERSION`）や形式の版が自分より新しい場合も、同じように止める

## 最初の1回（案）

- 同期を有効にする前に、端末内の全データを自動で書き出す（バックアップファイル）
- クラウドが空のとき → その端末のデータをそのまま送る
- クラウドにも端末にもデータがあるとき → 件数を見せたうえで「合流する／クラウドに揃える／この端末に揃える」から選ぶ。既定は「合流する」

## バックアップとの関係（案）

- 同期はバックアップの代わりにならない。誤って削除したデータも全端末に広がる
- 競合の控えと削除の印から、誤って消したものをある程度は戻せる
- Googleドライブはファイルの過去の版を一定期間残す（期間と条件は実装時に確認する）。補助としては使えるが、頼りきらない
- アプリ単位の書き出し機能（MANUSCRIPT・MINDFRAME・RECON）は今後も使い続ける

## 容量と通信量（案）

- 画像は中身から名前を作るので、変わったものだけを送ることになる
- 同期を有効にしたときに`navigator.storage.persist()`を求め、ブラウザに保存データを消されにくくする
- 1ファイルの大きさに上限を設け、超えたら同期せずに警告する
- Googleドライブへのアップロードは、5MBを超えるファイルでは分割アップロード（resumable upload）を使う

## 同期状態の表示（案）

- ヘッダーに同期の状態を出す：同期済み（最終同期時刻）／未送信あり／同期中／エラー／ログインが必要
- 失敗は黙って握りつぶさず、表示と同期の記録に残す

## OneDrive対応時のメモ

- アプリの登録にはMicrosoft Entraのテナントが要る。個人のMicrosoftアカウントだけでは登録できない。公式の手順では、テナントを持っていない場合は無料のAzureアカウントを作る
- 専用領域は`Files.ReadWrite.AppFolder`（OneDriveの「アプリ」フォルダ。Googleと違い、利用者からも見える）
- ログイン用のライブラリMSAL.js（MITライセンス）は、リポジトリに同梱できる。Googleと違い、外部から読み込まずに済む
- 単一ページアプリの場合、更新用トークン（refresh token）の有効期限は24時間。1日1回程度ログインし直す場面がありうる
- **案**：同期先は1つに絞る（両方に対応はするが、同時には使わない）。もう片方は将来、バックアップ専用として使う余地を残す

## 実装の段階（案）

1. 暗号化・形式・3方向比較を作る。保存先なしで、ファイルの書き出し・読み込みを使って2台の間で手動同期できるところまで。クラウドが使えないときの代わりの手段にもなる
2. Googleドライブに対応する（ログイン・自動同期）
3. 状態の表示と設定画面を仕上げる
4. OneDriveに対応する
