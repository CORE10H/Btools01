## 全体の構成（案）

- 同期は本体（`index.html`）で行う。新しいファイル：`js/sync.js`（同期の本体）、`js/sync-gdrive.js`（Googleドライブとのやり取り）
- 各アプリのDBは本体と同じオリジンなので、本体から開ける
- 保存先ごとの違いは「一覧・読む・書く・消す」の4操作に閉じ込める。OneDriveに対応するときは`js/sync-onedrive.js`を足すだけにする
- 端末内に同期の管理用DB `sideops_sync` を新設する。中身は端末ID、前回同期した時点の状態（レコードごとの指紋と版）、競合で負けた版の控え、同期の記録

### IndexedDB実装パターンとの関係（唯一の例外）

`platform/claude_IndexedDB実装パターン_仕様書.md`は「DB名は機能ごとに完全に独立させる（他アプリのデータへアクセスする手段自体を作らない）」としている。同期の本体はこの原則の**唯一の例外**として、すべてのDBを読み書きする。歯止めは次のとおり。

- 触れるのは、同期対象の一覧（許可リスト）にあるDBだけ
- 端末にまだ存在しないDBを`indexedDB.open(名前)`で開かない。版を指定せずに開くと空のDBが版1で作られ、後からアプリが開いたときに初期化（`onupgradeneeded`）が走らず、アプリが壊れる。存在の確認には`indexedDB.databases()`を使う
- アプリ側の版上げを妨げないよう、接続は使い終わったらすぐ閉じる。`onversionchange`を受けたら即座に閉じる

## クラウド上の形式（案・v1/v2共通）

### 置き場所

Googleドライブの`appDataFolder`（このアプリ専用の隠し領域）を使う。

- SIDE-OPSは利用者のほかのファイルに触れない。逆に、ドライブの画面からもこの領域は見えない
- 権限は`drive.appdata`だけを求める

### ファイルの構成

```
manifest.json      … 形式の版・暗号化の設定（ソルト・反復回数）・包んだデータ鍵・鍵の確認用データ（ここだけ暗号化しない）
device_<端末>.enc  … 端末の情報（端末名・最終同期時刻・アプリの版）
db_<端末>_<DB>.enc … その端末が持っている、そのDBの全レコード（削除の印を含む）
blob_<識別子>.enc  … 画像などのバイナリ。1点1ファイル
```

- ドライブはフォルダをたどるより名前で探す方が手数が少ないので、平らに並べて名前で区別する
- ファイル名には、中身を推測させる情報（DB名・端末名）を入れない。`<端末>` `<DB>` `<識別子>`は鍵付きハッシュ（HMAC）で作り、本当の名前は暗号化した中身に書く

### 各端末は自分のファイルにだけ書く

- 端末は、自分の端末IDのファイルにだけ書き込む。ほかの端末のファイルは読むだけ
- 2台が同じファイルに書くことがないので、保存先側の「上書き前の版確認」に頼らずに済む。Googleドライブがこの確認に対応しているかは、公式資料で確認できなかった
- 読むときは全端末のファイルを集め、レコード単位で合流させる
- 使わなくなった端末（機種変更など）のファイルは、設定画面から消せるようにする

### DBファイルの中身（暗号化する前）

```json
{
  "format": "sideops-sync-db",
  "formatVersion": 1,
  "db": "sideops_memo",
  "dbVersion": 1,
  "schema": {
    "entries":  { "keyPath": "id",  "indexes": [{ "name": "…", "keyPath": "…", "unique": false }] },
    "settings": { "keyPath": "key", "indexes": [] }
  },
  "appBuild": "2026-10-05",
  "device": "端末ID",
  "writtenAt": "2026-10-05T12:00:00.000Z",
  "stores": {
    "entries": [
      { "key": "m_…", "ver": "1759650000000-0000-端末ID", "value": { "…": "レコードそのまま" } },
      { "key": "m_…", "ver": "1759650000123-0000-端末ID", "deleted": true }
    ]
  }
}
```

- `schema`には、ストア名・キー・索引を記録する。アプリをまだ一度も開いていない端末でも、正しい形のDBを作れるようにするため。v2がデータの構造を知るためにも使う
- `value`はレコードをそのまま入れる。ただし、バイナリは参照に置き換える。
  - Blob → `{ "$sideopsBlob": "<識別子>", "type": "image/png", "size": 12345 }`
  - 画像のdata URL（壁紙・SCAFFOLD） → `{ "$sideopsDataUrl": "<識別子>", "type": "image/jpeg" }`。端末に戻すときは元のdata URLの文字列に戻す
- バイナリは値をたどって自動で見つけるので、アプリごとの設定は要らない。data URLとみなすのは、全体がdata URLの形で、一定以上の長さがある文字列だけにする（メモ本文などの誤判定を防ぐ）

### 画像（バイナリ）

- 1点1ファイルにする。名前は中身から作る鍵付きハッシュにする
- 同じ画像は1回しか送らず、変わっていない画像は送り直さない
- 名前が同じなら中身も同じなので、ファイルの書き換えが起きない。つまり、画像のファイルでは競合が起きない
- どこからも参照されなくなった画像は、すぐには消さず、一定期間（例：30日）たってから片付ける。ほかの端末がまだ参照している可能性があるため

### 圧縮

テキスト（DBファイル）は、暗号化の前にgzipで圧縮する（ブラウザ標準の`CompressionStream`を使う）。画像はもともと圧縮されているので、そのまま送る。

## 暗号化（案）

鍵を2段に分ける「封筒暗号化（envelope encryption）」という定番の方式を使う。

- **データ鍵**：ランダムに作るAES-256-GCMの鍵。すべてのファイルをこの鍵で暗号化する
- **データ鍵を包む鍵**：パスフレーズからPBKDF2-SHA256で作る（反復回数60万回。OWASPの推奨値）。データ鍵をこの鍵で包み、manifestに置く
- パスフレーズを変えても、データ鍵を包み直すだけで済む。全ファイルを暗号化し直す必要はない

細かい決まりは次のとおり。

- 暗号化のたびに、ランダムな初期化ベクトル（IV、96bit）を作る。同じIVは使い回さない
- 付加データ（AAD）に「ファイルの種類・DB・端末」を入れる。別の端末や別のDBのファイルとすり替えられたら検知できる
- ブラウザ標準のWeb Cryptoだけで作れる。Dart（v2）でも同じ方式を使える。独自の暗号は作らない

パスフレーズの歯止め：

- 最低の文字数を決める（例：12文字以上）。設定するときは2回入力して照合する
- 忘れた場合、クラウドのデータは誰にも復元できない。ただし、どれか1台の端末にデータが残っていれば、「同期をやり直す（新しいパスフレーズでクラウドを作り直す）」で復旧できる。致命的になるのは全端末を失った場合だけなので、書き出しによるバックアップと併用する

**データ鍵は端末に覚えさせる（2026-10-05決定）**

- 取り出せない形の鍵（non-extractableなCryptoKey）として`sideops_sync`に保存する。パスフレーズを入力するのは、その端末で同期を始めるときの1回だけ
- 理由：端末内には元から平文のデータがあるので、鍵だけを守っても効果が薄い
- 「この端末を忘れる」で、覚えた鍵と同期の状態を消せるようにする（端末内のアプリのデータは消さない）

**端末をなくしたときの歯止め**

- なくした端末は鍵（データ鍵そのもの）を覚えている。そのため、パスフレーズを変えるだけ（データ鍵を包み直すだけ）では、その端末を締め出せない
- 残った端末から「データ鍵を作り直す」を実行できるようにする。新しいデータ鍵で全ファイルを暗号化し直し、なくした端末のファイルも消す。パスフレーズの変更とは別のボタンにする
- あわせて、Googleアカウントの設定画面から、なくした端末のログインを取り消す（利用者の操作。手順を画面に案内する）

## 認証（Google）

- 求める権限は`drive.appdata`だけ。Googleの分類では「機密でない」権限で、厳しい審査は要らない
- アクセストークンは約1時間で切れる。メモリにだけ置き、IndexedDBには保存しない。切れたら取り直す
- SIDE-OPSは誰でも開けるページだが、Google側のアプリ登録を「テスト中」のままにして、テストユーザーを自分だけにする。他人がSIDE-OPSを開いてもログインできない（歯止め）。SIDE-OPSを配布する段階になったら見直す

### ログイン方式（2026-10-05決定：A）

| 方式 | 内容 | 長所 | 短所 |
|---|---|---|---|
| A. 公式ライブラリ（GIS） | Googleが推奨するブラウザ向けライブラリ（`accounts.google.com/gsi/client`）を読み込む | 公式に推奨され、保守されている | Googleのサーバーから読み込んだスクリプトが、SIDE-OPSと同じオリジンで動く。理屈の上では全アプリのデータと鍵に手が届く。RECONの「顧客データを扱うページに外部サーバーのスクリプトを入れない」方針と衝突する |
| B. ライブラリを使わず直接 | Googleのログイン画面へ移り、戻ってきたURLからトークンを受け取る（implicit flow） | 外部のスクリプトが一切入らない | Googleが「安全でない」「旧方式の互換と調査のためだけに提供している」と明記している。将来止められる可能性がある |
| C. 認可コード＋PKCE | 現在の一般的な推奨方式 | ― | Googleの「ウェブアプリケーション」の種類では、PKCEを使ってもクライアントシークレットが必須。サーバーのないSIDE-OPSでは秘密を守れない。**不採用** |
| D. 別のオリジンでログインだけ行う | ログイン専用の小さなページを別のオリジン（例：無料で作れるGitHub組織のPages）に置き、そこでGISを使ってトークンを受け取り、SIDE-OPSへ`postMessage`で渡す | Googleのスクリプトが、SIDE-OPSのオリジンでは一切動かない | GitHub組織とリポジトリが1つずつ増える。ログイン時にポップアップが2段になる |

**決定：A**。Googleのスクリプトを受け入れる。RECONの「顧客データを扱うページに外部サーバーのスクリプトを入れない」方針は、RECONのページ自体については今後も守る。顧客データを含む全データを送るのは本体ページになるため、本体ページについてはこの方針の例外とする。

採用の条件：

- GISはリポジトリに同梱できず、毎回Googleのサーバーから読み込む。読み込んだスクリプトはSIDE-OPS自身のコードと同じ権限で動く（ログインだけに閉じ込める仕組みはない）。これを承知のうえで採用する
- 読み込むのは本体ページだけ、それも同期を有効にしている間だけにする。同期を使わない端末では一切読み込まない
- 本体ページにCSP（読み込み元の許可リスト）を設け、スクリプトは自前とGoogleのログイン用だけに絞る。XSS対策としても効く
  - 本体ページにはインラインのスクリプトがない（2026-10-05確認）ので、`script-src`は絞れる
  - LOGパネルは利用者が設定したURLから取得するため、`connect-src`は取得先を事前に列挙できない。どこまで絞るかは実装時に決める
  - GISが必要とする読み込み先（ポップアップ・iframe等）は実装時に確認して許可リストを作る

### インポートしたhtmlとの関係

ランチャーでインポートしたhtml（後天的アプリ）は`srcdoc`で表示され、sandboxの指定がないため本体と同じオリジンで動く（`core/claude_アプリランチャー_仕様書.md`）。今でも全アプリのDBを読めてしまうが、同期を入れると、覚えた鍵やGoogleのトークンにも手が届く。既存の決まり「**自作以外のhtmlはインポートしない**」が、さらに重要になる。

## 同期のタイミング（案）

- **取り込み（クラウド→端末）**：起動したとき、タブが再び表示されたとき（`visibilitychange`）、手動のボタン
- **送り出し（端末→クラウド）**：
  - 変更があってから一定時間（例：30秒）操作がないとき
  - タブが隠れたとき。スマホでは最後まで終わらないことがあるので、できる範囲で行う
  - 手動のボタン
- **変更の検知**：
  - 各アプリは、保存のたびに本体へ「変更あり」と知らせる。テーマブリッジと同じ`postMessage`の仕組みを逆向きに使い、共通スクリプトに関数を1つ足す
  - 知らせが漏れても、起動時と送り出しの前に全DBを前回同期時点と比べ直すので、取りこぼさない
- **複数のタブ**：同じ端末で複数のタブが開いていても、同期を動かすのは1つだけにする（ブラウザ標準のWeb Locks APIで排他する）
- **基本の使い方**：端末を同時に使わないので、別の端末に移る前に「今すぐ同期」を押すのを基本にし、自動同期はその保険とする

## 変更の判定と競合（案）

### 3方向比較

前回同期した時点の状態（各レコードの指紋＝内容のハッシュと版）を`sideops_sync`に控え、今の状態と比べる。Unisonなどの同期ツールで使われている定番の方式。

- 前回はあったが今はない → 削除された → 削除の印を作る。**アプリ側の削除処理は変えなくてよい**
- 指紋が変わった → 更新された → 新しい版を付ける

### 版の付け方

- 端末の時計の時刻に、「今まで見た中で最大の版より必ず大きくする」補正をかける（Lamport時計の考え方）
- 時計が遅れている端末でも、同期した後の編集は必ず新しいと判定される
- 版は同期の側で付けるので、アプリごとの`updatedAt`の有無に左右されない（プロンプトギャラリー2種とDiscoticaには`updatedAt`がない）

### 合流と競合

- 合流するときは、レコードごとに版の大きい方を採用する
- 両方の端末で同じレコードを変えていた場合（競合）も、版の大きい方を採用する。負けた方は`sideops_sync`の「競合の控え」に一定期間（例：30日）残し、設定画面から確認・復元できるようにする
- 削除の印は、すべての端末が受け取ったと確認できるまで残す。その後、一定期間（例：90日）たってから片付ける

## 開いているアプリとの関係（案）

- Stageで開いているアプリのDBには、同期で書き込まない。アプリが閉じられたら反映する
- 待っている間は「ほかの端末の変更が届いています（アプリを閉じると反映します）」と表示する
- 端末を同時に使わない前提では、取り込みは主に起動直後（アプリを開く前）に起きる。この待ちが発生するのはまれ
- MINDFRAMEが持っている「保存直前の衝突確認」は、このときの2重の歯止めとして働く

## 同期の単位と対象

単位はDB（＝アプリ）ごと。設定画面で、DBごとに同期のオン・オフを切り替えられるようにする。

| DB | 初期値 | 理由・メモ |
|---|---|---|
| `sideops_launcher` | 同期する | |
| `sideops_settings` | 一部だけ同期する（2026-10-05決定） | 下の「本体の設定の分け方」を参照 |
| `sideops_log` | 同期しない（案） | 両方の端末で取得すると、取得先へのアクセスが倍になる。通知は取得先から取り直せる |
| `sideops_mindframe` | `views`以外を同期する（案） | `views`は表示位置・ズーム。画面の大きさが違うので端末ごとに持つ |
| `sideops_recon` | 同期する（2026-10-05決定） | 下の「RECONを同期するときの扱い」を参照 |
| その他のアプリ | 同期する | |

### 本体の設定の分け方（2026-10-05決定）

`sideops_settings`は、同じレコードの中に「同期する項目」と「端末ごとの項目」が混ざっているため、項目単位で分ける。

| レコード | 項目 | 扱い |
|---|---|---|
| `main` | `themeKey`・`customThemeTokens`・`eyedropperThemeTokens` | 同期する |
| `main` | `panelAlpha`（パネルの透過率）・`wallpaperValue`（選んでいる壁紙） | 端末ごと |
| `wallpaperUploads` | アップロードした壁紙画像（全体） | 端末ごと（同期しない） |

- ほかの端末から設定が届いたら、同期する項目だけを書き換え、端末ごとの項目はその端末の値を残す
- スポイトで作ったテーマ（`eyedropperThemeTokens`）は、作った端末の壁紙から生成した色の値をそのまま同期する。壁紙は端末ごとなので、ほかの端末では壁紙とテーマの元が一致しないことがあるが、色は保存した値のまま変わらない
- 新しい項目を`main`に足すときは、同期するか端末ごとかを必ず決め、この表に書き足す。決めていない項目は端末ごととして扱う（知らない項目を勝手に広げない）

### RECONを同期するときの扱い（2026-10-05決定）

- 購入者（第三者）の個人情報を含むが、暗号化して送る前提で同期に含める
- RECONのページ自体は、今後も通信を全面禁止にしたまま（CSPの`connect-src 'none'`）。データを読んで送るのは本体の同期機能
- 同期をオンにしたあと、RECONを初めて送る前に「顧客データを含みます。暗号化して送ります」と1回だけ確認する
- RECONの仕様書（`apps/claude_アプリ_RECON_仕様書.md`）の「端末ごとのデータ」の記述は、同期の実装時に書き換える

テーマブリッジの一時データ（sessionStorage）は対象外。

## アプリのバージョン差（案）

- 本体に「アプリの版」（日付の文字列）を持たせ、各端末のファイルに記録する
- 自分より新しい版の端末が書いたファイルを見つけたら、そのDBの取り込みと送り出しを止め、「SIDE-OPSを再読み込みして更新してください」と表示する。古い版が新しい項目を知らずに上書きし、その項目が消えるのを防ぐため
- DBの版（`DB_VERSION`）や形式の版が自分より新しい場合も、同じように止める

## 最初の1回（案）

- 同期を有効にする前に、端末内の全データを自動で書き出す（バックアップファイル）
- クラウドが空のとき → その端末のデータをそのまま送る
- クラウドにも端末にもデータがあるとき → 件数を見せたうえで「合流する／クラウドに揃える／この端末に揃える」から選ぶ。既定は「合流する」

## バックアップとの関係（案）

- 同期はバックアップの代わりにならない。誤って削除したデータも全端末に広がる
- 競合の控えと削除の印から、誤って消したものをある程度は戻せる
- Googleドライブはファイルの過去の版を一定期間残す（期間と条件は実装時に確認する）。補助としては使えるが、頼りきらない
- アプリ単位の書き出し機能（MANUSCRIPT・MINDFRAME・RECON）は今後も使い続ける

## 容量と通信量（案）

- 画像は中身から名前を作るので、変わったものだけを送ることになる
- 同期を有効にしたときに`navigator.storage.persist()`を求め、ブラウザに保存データを消されにくくする
- 1ファイルの大きさに上限を設け、超えたら同期せずに警告する
- Googleドライブへのアップロードは、5MBを超えるファイルでは分割アップロード（resumable upload）を使う

## 同期状態の表示（案）

- ヘッダーに同期の状態を出す：同期済み（最終同期時刻）／未送信あり／同期中／エラー／ログインが必要
- 失敗は黙って握りつぶさず、表示と同期の記録に残す

## 段階1の実装（2026-10-05）

### ファイルと画面

- `js/sync.js`：同期の本体と画面。`index.html`の最後で`main.js`の後に読み込む。読み込めなかった場合、ヘッダーの☁ボタンは無効のまま
- 同期モーダル（`#syncOverlay`）と、確認・パスフレーズ入力のダイアログ（`#syncDialog`）は`index.html`に置き、見た目は`style.css`の「同期モーダル」節に書く
- モーダルの中身：この端末の名前（ほかの端末に表示される）、同期の鍵の有無・最後の同期・競合の控えの件数、「同期ファイルを読み込む」「新しく作る」、同期するデータのオン・オフ、バックアップ・その他（全データを書き出す／バックアップから復元／競合の控えを書き出す／この端末を忘れる）

### 使い方

1. 最初の端末：☁ →「新しく作る」→ パスフレーズを決める（12文字以上・2回入力）→ 全データのバックアップを保存 → 同期ファイル（`sideops-sync-YYYYMMDD-HHMMSS.json`）が保存される
2. 別の端末：☁ →「同期ファイルを読み込む」→ パスフレーズ → バックアップを保存 → 取り込み。自分の分を書き足した新しい同期ファイルが保存される
3. 以降、端末を移るとき：移る前の端末で、手元の最新の同期ファイルを「読み込む」（自分の変更を書き足した新しいファイルが保存される）→ そのファイルを次の端末で「読み込む」

「新しく作る」は、最初の1回か、手元に同期ファイルがないときだけ使う。ほかの端末が書き足した分が入らないため、鍵を持っている端末で押すと、その旨を確認してから作る。

### 同期ファイルの形式

```json
{ "format": "sideops-sync-package", "formatVersion": 1, "spaceId": "…", "exportedAt": "…", "files": { "ファイル名": "base64" } }
```

`files`の中身は、段階2以降でクラウドに置くファイル群とまったく同じ。同期ファイルは、それを1つにまとめただけのもの。

| ファイル名 | 中身 |
|---|---|
| `sideops-sync-manifest.json` | 形式の版・spaceId・keyId・鍵の作り方（PBKDF2の反復回数とソルト）・包んだ主鍵。**ここだけ暗号化しない**（秘密は含まない） |
| `d_<HMAC 32桁>.bin` | 端末の情報（端末ID・端末名・SIDE-OPSの版・どのDBのファイルを持っているか） |
| `b_<HMAC 32桁>.bin` | その端末の、そのDBの全レコード（削除の印を含む）と、全ストアの形 |
| `x_<HMAC 64桁>.bin` | 画像などのバイナリ1点 |

### 暗号の手順（v2のDartでも同じ手順で読み書きする）

- **主鍵**：ランダムな32バイト。パスフレーズ（**NFKC正規化**する）からPBKDF2-SHA256（60万回、ソルト16バイト）で作ったAES-256-GCMの鍵で暗号化し、manifestに置く（AAD：`sideops-sync|wrap|<spaceId>`）
- 主鍵からHKDF-SHA256（salt `sideops-sync/v1`、info `enc`／`name`）で、暗号化用のAES-256-GCM鍵と、名前用のHMAC-SHA256鍵を作る。keyIdは`HMAC(名前用の鍵, "key-id")`の先頭16桁
- 端末には、取り出せない形（non-extractable）の2つの鍵を`sideops_sync`に保存する。主鍵そのものは保存しない
- ファイル名：端末＝`HMAC("device|<端末ID>")`、DB＝`HMAC("db|<端末ID>|<DB名>")`、画像＝`HMAC(画像のバイト列)`
- 暗号文の形：`SOS1`（4バイト）＋IV（12バイト、毎回ランダム）＋AES-GCMの暗号文（認証タグ込み）。AADは`sideops-sync|<spaceId>|<ファイル名>`で、ファイル名と結び付ける（別のファイルとすり替えると復号できない）
- 端末の情報とDBのファイルは、JSONをgzipで圧縮してから暗号化する。画像は圧縮せずに暗号化する。画像は復号したあと、名前（HMAC）と中身が一致するかも確かめる

### レコードの持ち方

- DBのファイルの各レコード：`{ key, ver, value }`。削除の印は`{ key, ver, deleted: true }`
- `value`はレコードをそのまま入れる。ただし、次のものは参照（目印のオブジェクト）に置き換える。端末に戻すときは元の形に戻す
  - Blob／File → `{ $sideopsBlob: 識別子, type, size, fileName?, lastModified? }`
  - 画像のdata URL（1024文字以上で、元の文字列に正確に戻せるものだけ） → `{ $sideopsDataUrl: 識別子, prefix }`
  - Date → `{ $sideopsDate }`、NaN・Infinity → `{ $sideopsNum }`、ArrayBuffer・Uint8Array → `{ $sideopsBytes }`
  - Map・Setなど、ほかの種類を含むレコードは同期せずに飛ばす（結果に件数を出す）。`$sideops`で始まる項目名を含むレコードも飛ばす
- 指紋：目印に置き換えた後の値を、キーの順序を固定したJSONにしてSHA-256を取る
- キー：文字列・数値・それらの配列だけを扱う

### 版

- 形式：`時刻13桁-カウンタ4桁-端末ID16桁`。文字列のまま大小を比べられる
- 新しい版は「端末の時計」と「今まで見た最大の版」の大きい方から作る（Lamport時計の考え方）。時計が2時間遅れた端末の編集でも、同期した後の編集なら勝つことを確認した
- その端末で初めて同期するDBでは、レコードの`updatedAt`→`updated`→`createdAt`の順に、あるものを版の時刻に使う
- どれも持たないレコード（本体の設定`main`など）は、次のように扱う
  - すでにある同期に後から加わる側で、同期側に同じレコードがある場合 → `0000000000000-0000-0000000000000000`にする（必ず負ける＝同期側の内容を採用する）
  - それ以外 → 時刻0と自分の端末ID
  - この規則を入れた理由：実装の確認で、本体の設定（更新日時がない）のテーマが、端末IDの大小という偶然で勝ち負けしていたため

### 段階1の割り切り（計画との違い）

- **最初の1回**：「合流／クラウドに揃える／この端末に揃える」の選択は作らず、常に合流する。負けた方は競合の控えに残る。初回の前に全データのバックアップを保存するので、元に戻したいときは「バックアップから復元」を使う
- **開いているアプリ**：アプリへの通知はまだ作らない。代わりに、Stageでアプリを開いている間（閉じた直後の保存の猶予を含む）と、他のタブでSIDE-OPSを開いている間（`BroadcastChannel`で確認）は、同期しない
- **取り込んだ後**：モーダルを閉じると再読み込みする。本体（ランチャー・設定）が古いデータを持ったまま保存し直すのを防ぐため
- **競合の控え**：書き出し（JSON）だけ。画面で確認・復元するのは段階3
- **パスフレーズの変更・データ鍵の作り直し**：段階3
- **画像の片付け**：同期ファイルでは、どこからも参照されない画像をその場で消す。この端末で同期しない設定にしたDBが参照している画像も残す。クラウドでは、他の端末が書き込み途中の可能性があるので猶予を置く（段階2）
- **DBの版が違うとき**：端末どうしでDBの版（`DB_VERSION`）が違う場合、そのDBは合流しない（移行前の形のデータで上書きしないため）。結果に「古い方の端末でアプリを一度開いてから同期してください」と出す
- **端末にないDB**：同期ファイルに記録された全ストアの形（同期しないストアも含む）で作る。ただし、記録された版がこの版のSIDE-OPSの知っている版と同じ場合に限る

### バックアップ（`sideops-backup-*.json`）

- 同期の対象のDB（許可リスト）を、ストア丸ごと（端末ごとの項目・同期しないストアも含む）書き出す。**暗号化しない**。画像はSHA-256の名前で、base64にして入れる
- 復元は、DBごとの件数を見せて確認したうえで、DBごとにストアを空にしてから書き戻す（1DB＝1トランザクション）。DBの版が違うDBは復元しない
- 同期を使っている場合、復元した内容は、次の同期でほかの端末にも広がる

### 開発時の決まり（重要）

- アプリの`DB_VERSION`を上げたら、`js/sync.js`の`DB_RULES`の`version`も同じ値にし、`SYNC_APP_BUILD`（`yyyymmddnn`の数値）を上げる
- アプリのレコードの項目（データの形）を変えたら、`SYNC_APP_BUILD`を上げる
- 新しいアプリ（新しいDB）を足したら、`DB_RULES`に足す。足さないと同期されない
- 本体の設定（`main`）に項目を足し、それを同期したいときは、`DB_RULES`の`only`に書き足す。書き足さない項目は端末ごとになる

### 動作確認

- 確認キット：`D:\dev\sideops_sync_verify\`（リポジトリの外。`cdp.dart`はRECONのキットからの流用）
- 実行：`dart sync_e2e.dart <Btools01のフォルダ> <作業フォルダ>`
- 内容：使い捨てプロファイルのヘッドレスEdgeを2つ（端末A・B）立ち上げ、同じローカルサーバーで受け渡しを確かめる。2026-10-05時点で66項目がすべてOK
- 主な確認項目
  - 各アプリのDBの版が許可リストの版と一致する
  - パスフレーズの規則（短い・2回の入力が違う・違うパスフレーズは受け付けない）

  - この端末を忘れると鍵がなくなる

## 段階2の実装（2026-10-05）

※画面は、OneDriveの実装で「クラウドで同期」にまとめた（保存先で「Googleドライブ」を選び、「同期する」を押す）。以下の「Googleドライブで同期」は、その操作のこと。

### ファイル

- `js/sync-gdrive.js`：Googleドライブとのやり取り（ログイン・list/read/write/remove）。`sync.js`より前に読み込む
- クライアントIDは`js/sync-gdrive.js`の`CLIENT_ID`に書く（秘密ではない）。**空の間は「準備中です（Google Cloudの登録待ち）」と表示し、ボタンを押せない**
- Googleのログイン部品（GIS、`https://accounts.google.com/gsi/client`）は、「Googleドライブで同期」を押したときに初めて読み込む。同期を使わない端末では読み込まない

### 使い方

- 最初の端末：☁ →「Googleドライブで同期」→ Googleにログイン（ポップアップ）。そのあとは端末の状態によって分かれる
  - 同期ファイルで使っていた鍵がある場合：その同期（同じパスフレーズ）をドライブに置く。確認を1回出す
  - 鍵がない場合：パスフレーズを決める
- ほかの端末：☁ →「Googleドライブで同期」→ ログイン → パスフレーズを入力
- 以降：**☁を押すだけで同期する**（つないでいる端末では、モーダルを開いたときに同期を始める。ログインが切れていればログインから）
- 「接続を解除」で、その端末はドライブと同期しなくなる（ドライブ上のデータと端末のデータは消えない）。ドライブ上のデータそのものは、Googleドライブの設定（アプリの管理）から消せる

### 自動の同期

- ログイン中（トークンが有効な約1時間）だけ動く。ログインのポップアップは押したときにしか開けない（ブラウザの決まり）ため、自動ではログインし直さない
- 動くとき：画面を離れたとき（`visibilitychange`→hidden）、戻ったとき（前回の自動の同期から1分以上）、Stageでアプリを閉じたとき（保存の猶予の後）、5分ごと
- 動かないとき：Stageでアプリを開いている間、設定などのモーダルを開いている間、他のタブでSIDE-OPSを開いている間、接続していない／「自動で同期する」を外したとき
- 確認が必要な場面（パスフレーズ、顧客データを初めて送る確認）では何もしない。RECONの確認がまだなら、RECONだけ飛ばして「確認待ち」と記録する
- ほかの端末の変更を取り込んだら、「再読み込みします」と表示して再読み込みする（アプリやモーダルを開いている間は、閉じるまで待つ）

### ドライブとのやり取り

- 一覧：`GET /drive/v3/files?spaces=appDataFolder`（ページ送りに対応）。同じ名前のファイルが複数あれば、読むときは新しい方を使い、書くときは1つに揃えて残りを消す
- 新規：`POST /upload/drive/v3/files?uploadType=multipart`（`parents: ['appDataFolder']`）。書き換え：`PATCH /upload/drive/v3/files/{id}?uploadType=media`。削除：`DELETE /drive/v3/files/{id}`
- 5MBを超えるファイル：分割アップロード（`uploadType=resumable`→`Location`のセッションURLへ`PUT`）。セッションURLを受け取れなければ、通常のアップロードに切り替える
- 401（ログイン切れ）：トークンを捨てて「もう一度押してください」と表示する。429・5xx（混雑・一時的な障害）：間隔を広げながら最大4回までやり直す
- アクセストークンはメモリにだけ置く（保存しない）

### 段階2で足した、両方の保存先に共通の仕組み

- **変わっていないファイルは書き直さない（クラウドだけ）**：前回書いたときの「中身の要約（`writtenAt`を除いたSHA-256）」と「保存先での更新時刻・大きさ」が両方一致すれば省く（`sideops_sync`の`written`）。同期ファイルは、古いファイルを読み込み直した場合に備えて毎回すべて書く
- **DBのファイルの並び順をキーの順に固定する**：実装の確認で、取り込んだ直後と次の回とでレコードの並びが変わり、中身が同じなのに書き直していたため
- **使わなくなった画像の片付け**：クラウドでは、最後に書き換えられてから30日たった、どこからも参照されない画像だけを消す（ほかの端末が書き込み途中の可能性があるため）
- **重複の候補を知らせる**：初めての合流のとき、ID・作成日時・更新日時を除いた中身が同じで、IDが違うレコードが両方の端末にあれば、「同じ内容で別々のIDのデータがn件あります」と知らせる。両方の端末で別々に登録した同じデータ（例：DiscoticaのアーティストをPCとAndroidで別々に登録していた）は、IDが違うので合流すると両方残る。不要な方を消すと、その削除がほかの端末にも届く
  - きっかけ：実機での確認後、ユーザーから「Discoticaのアーティストが増えたように見える」と報告（2026-10-05）。同期はIDの違うレコードを作らないことを確認したうえで、別々に登録していたデータの合流が原因の可能性が高いと判断した

### 未決定（ユーザー判断待ち）

### ログイン（OAuth 2.0 認可コード＋PKCE、標準の手順を自前で実装）

- Microsoftの公式ライブラリ（MSAL.js）は使わない
  - 今の版（v5）はES Modules／CommonJSでしか配布されず、ビルドの道具（Node.js）がないこのPCでは同梱しにくい
  - 使う範囲が狭く（ログインして、アプリのフォルダを読み書きするだけ）、手順そのものは標準規格（RFC 6749・7636）
  - 外部のスクリプトを本体ページで読み込まずに済む（RECONの方針を本体ページでも守れる）

  - ポップアップより、スマホでも確実に動くため
  - 戻ったら、URLからすぐにコードを消し、同期の続きをする
- ログインに出る前に、Stageでアプリを開いていないか・ほかのタブがないかを確かめる（ページを離れるため、入力中の内容を失わないように）
- `state`（ランダム）とPKCEの検証用の値は`sessionStorage`に置き、戻ったら照合して消す（10分以上前の要求は受け付けない）
- アクセストークン（約1時間）はメモリだけに置く
- 更新用トークンは、単一ページアプリでは最初のログインから24時間で切れ、取り直しても延びない。これを同期の鍵（AES-GCM）で暗号化して`sideops_sync`の`secret:onedrive-refresh`に保存する
  - 24時間の間は、ページを開き直してもログインし直さずに同期できる（自動の同期も続く）
  - 鍵がまだない端末（初めての同期の途中）ではメモリだけに置き、同期が終わって鍵ができた後に保存する
  - 「接続を解除」「この端末を忘れる」で消す
- 401は、更新用トークンで1回だけ取り直す。更新用トークンも切れていたら「ログインが必要」（☁が黄色）にする。自動ではログイン画面へ移らない

## 軽量化・お知らせ・取り消し（2026-10-06）

ユーザーから「一日使ったら重い」と報告があった。原因は次の2つ。
- 同期のたびに、全アプリの全データ（画像も含む）を読み直していた
- もう一方の端末のファイルを、変わっていなくても全部ダウンロードし、それを5分ごと・画面を行き来するたびに行っていた

ユーザーと詰めた設計（A：軽くする／B：知らせる／C：戻せるようにする）を実装した。この節の内容が、それより前の節の「自動の同期」「段階1の割り切り（開いているアプリ）」などより優先する。

### A：軽くする

**変わったものだけを扱う**
- **クラウド側**：一覧を取るときに付いてくる版の印（OneDriveはeTag）を、取り込んだ時点の印として`sideops_sync`の`seen`に控える。印が変わっていないほかの端末のファイルはダウンロードしない
  - 端末の目次は、中身（DBの一覧・最後に送った時刻）も控えて使い回す
  - DBのファイルは、DBの版と参照している画像の一覧を控える（画像の片付けに使う）
  - 取り込まなかったファイル（同期しない設定・DBの版違い・顧客データの確認待ち）は「取り込み済み」にしない
- **端末側（「変えたよ」の印）**：アプリがIndexedDBに書き込むと、`localStorage`に`sideops_sync_dirty:<DB名>|<ストア名>`＝時刻を残す
  - アプリ側の印は`apps/sideops-theme-bridge.js`（全アプリが読み込む）、本体側の印は`js/sync.js`が付ける
  - 同期は、印の時刻が前回見直した時刻（`sideops_sync`の`scanned`）より新しいDBだけを見直す
  - 同期しないストア（MINDFRAMEの`views`、本体の設定の`main`以外）への書き込みは数えない
  - 本体の設定は、端末ごとの項目（壁紙・透過率）だけを変えたときにも印が付く。そのため「未送信」の判定では、同期する項目が本当に変わったかを確かめる（1件だけ読む）
  - 同期が自分で書き込む分（受け取り）は、印を付けない元の関数で書く
  - 印の付け忘れに備えて、☁を押したときと1日1回は、印に関係なくすべてを見直す
- 変わっていないDBは開きもしない。これが一番の軽量化
- 件数の多いDBを見直すときは、25件ごとに画面の処理へ順番を譲り、画面が固まらないようにする

**自動の同期のタイミング**（5分ごとの同期はやめた）

| きっかけ | すること |
|---|---|
| SIDE-OPSを開いたとき | ログイン中なら裏で同期する（受け取り）。ログインが切れていたら止めて確かめる（Bの「開いたとき」） |
| しばらく（10分）離れて戻ったとき | 開いたときと同じ扱い（ページが開いたままのスマホで、ほかの端末で作業していた場合のため） |
| 画面から離れるとき（アプリの切り替え・画面のロック） | 未送信があれば送る。スマホでは途中で止められることがあり、その分は次回送る |
| Stageでアプリを閉じたとき | 保存の猶予の後、未送信があれば送る |
| アプリを開いたまま30分 | 未送信があれば「送るだけ」 |
| ☁を押したとき | すべてを見直して同期する（手動） |

- 「SIDE-OPSを閉じたとき」には同期しない。ブラウザが時間のかかる処理をさせてくれないため。代わりに未送信を表示して、手動の同期を促す（B）

**送るだけの同期（`pushOnly`）**
- アプリを開いている間に使う。データ帳を読んで送るだけで、何も書き換えない
- ほかの端末のファイルは読まない（受け取りは、アプリを閉じた後に回す）
- 送った後も「送信済み」にしない。変更前の版（`baseVer`）を残し、次の通常の同期で競合を見分けられるようにする
- まだ一度もほかの端末と合流していないDBには触らない

**同期の途中でアプリが開かれたら**
- そのDBへの受け取りは次の同期に回す（`canApply`）。何も保存せずに、そのDBを飛ばす

**再読み込み**
- ランチャー・本体の設定（本体が画面に持っているDB）を受け取ったときだけ再読み込みする
- アプリのデータは、アプリを開くときに読み直されるので、再読み込みしない

**端末の目次の「最後に送った時刻」**
- 端末の目次に`lastWriteAt`（実際にDBのファイルを送った時刻）を足した。ほかの端末に「最終送信」として見せる
- 古い版のSIDE-OPSは読み飛ばすので、形式の版は上げていない

### B：知らせる

**手動の操作は、中央のモーダルで知らせる**（`#syncProgress`）
- ☁の画面の一番下にあった結果の欄をやめ、☁の画面の上に重ねて出す（スマホでスクロールしないと見えず、気づかなかったため）
- 中身：進み具合（「メモを確認しています…」など）→ 結果（受け取り・送り出しの内訳など）→「OK」
- ☁を押して始めた同期は、「OK」で☁の画面も一緒に閉じる
- 1分以上かかったら「待つ／裏で続ける」を出す。裏で続けた場合、結果は帯で知らせる
- 自動の同期の途中に手動の操作をしたら、自動の方が終わるのを待ってから始める（「別のタブで同期中です」と誤って出さないため）

**自動の同期は、ヘッダーの下の帯で知らせる**（`#syncBanner`）
- 同期中は進み具合を出す。終わると「同期しました（受け取り○件・送り出し○件）」または「最新です」を出し、4秒で消える
- 失敗したときは「もう一度／閉じる」付きで、押すまで出したままにする
- 画面の下ではなく上に出す。下は見落としやすく、スマホではブラウザのツールバーに隠れるため
- 操作の邪魔はしない（☁の画面などより下に重なる）

**未送信の表示**
- ☁に黄色の印を付ける（題名に「未送信の変更があります（アプリ名）」）
- ログインが切れているなど、自動で送れないときは、帯で「未送信の変更があります　［今すぐ同期］［あとで］」を出す
  - 「あとで」の後は、新しい変更があるまで出さない
  - アプリで作業している間は帯を出さない（☁の印だけ）
- ☁の画面の状態欄にも「この端末の未送信」「ほかの端末（最終送信 ○時○分）」を出す

**開いた直後の同期の間は、アプリを開くのを待ってもらう**
- `main.js`の`openStage`の頭で`window.SideOpsSyncGate`を呼ぶ
- 同期中なら開くのを預かり、帯に「終わったらアプリを開きます　［待たずに開く］」を出す。終わったら預かったアプリを開く
- ランチャー・本体の設定を受け取って再読み込みする場合は、預かったアプリは開かない（もう一度押してもらう）

**開いたときにログインが切れていたら**（OneDriveの更新用トークンが24時間を過ぎた・Googleは開き直すたび）
- 覚えているログインが本当に使えるかは、取り直してみるまで分からない。開いたときに取り直してみて、だめなら止めて確かめる
- まず、ログインしなくても分かることを見せる：「前回の同期」「この端末の未送信」と、［ログインして確認］［同期せずに作業する］
- ［ログインして確認］：ログインしてから、ほかの端末の目次の版の印だけを見て、新しく送られたデータがあるかを確かめる（軽い）
  - あれば「○○が○時○分に送ったデータがあります（クラウドの方が新しい）　［同期する（おすすめ）］［同期せずに作業する］」
  - なければ「最新です」を出して閉じる。この端末に未送信があれば、裏で送る
- ［同期せずに作業する］：閉じて、☁は「ログインが必要」の黄色の印のままにする

### C：戻せるようにする（同期の記録）

- 同期で受け取ってこの端末のデータを書き換えたとき（追加・変更・削除）、**書き換える前の中身**を`sideops_sync`の`journal`ストアに残す（画像も含む。`sideops_sync`のDBの版を2に上げた）
- 30日、100件、合計およそ50MBを超えたら、古いものから消す
- ☁の画面の「同期の記録」に、最近の8件を出す。各記録に［すべて戻す］と、アプリが複数あれば［（アプリ名）だけ戻す］を付ける
- 戻す前に確認する。その記録で受け取ったデータを、受け取った後にこの端末で変更していたら（同期の直後の指紋と今の指紋が違ったら）、［変更した分も戻す］［変更していないものだけ戻す］を選んでもらう
- 本体の設定は、端末ごとの項目（壁紙など）は今のまま残し、同期する項目だけを戻す
- 戻したこと自体が「この端末の変更」（「変えたよ」の印が付く）になり、次の同期でほかの端末にも届く
- 戻した記録には「取り消し済み」と表示する
- 1件ずつ選んで戻す機能は、まだない（アプリ単位まで）
- 「この端末を忘れる」で記録も消す
