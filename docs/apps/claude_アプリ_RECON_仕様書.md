# アプリ：RECON（`apps/recon.html`）販売データの取込・分析 仕様書

## 概要

販路（まずはnote）の販売データCSVを取り込み、売上の集計・顧客の購入履歴・作品ごとの売上の分析に使う先天的アプリ（`builtin`）。

- 名前の由来：**RECON**ciliation（突合・照合）。CSVの数字と販路の管理画面の数字を「検算」し、表記の揺れた購入者・作品を「名寄せ」するのが仕事の中心であることから
- ランチャー表示名：`RECON`（`BUILTIN_APP_CHOICES`）。カバー画像は`apps/img/recon.jpg`（900×502、2026-10-02追加。ユーザー提供の1376×768を他のアプリのカバーと同じ大きさに縮小）
- テーマ追従：`<head>`で`sideops-theme-bridge.js`を読み込む
- `sideops:stage-closing`（Stageを閉じる合図）への対応は不要：保存は「取り込む」ボタンでの一括書き込みだけで、自動保存の待ちが存在しない。書き込みの途中でStageを閉じられた場合も、トランザクションが中止されて「何も保存されない」だけ（半端な状態は残らない）
- 外部ライブラリ：CSV解析にPapa Parse 5.7.0（MIT、CSV解析の定番）を使う。**CDNではなくリポジトリに同梱**（`apps/vendor/`）。顧客データを扱うページに外部サーバーのスクリプトを入れないため

## データの持ち場所（設計判断）

**データの正本はRECONのDB（`sideops_recon`）が持つ。INTELパネルは段階2で「集計済みの要約」だけを受け取って表示する。**

INTELパネル側に正本を置く案は、次の理由で不採用とした。

- INTELは1列3行の小さな表示面で、名寄せ・分析の画面を置く場所がない
- パネル側に正本を置くと、編集はアプリ・保存はパネルという往復の通信が必要になり、壊れ方が読みにくくなる
- スマホ版レイアウトではINTELパネル自体が非表示になる（`レスポンシブ対応_仕様書.md`）
- タスクパネル⇄DONE MOREと同じ方針（パネルは表示だけ、データはアプリ）にそろえられる

本体（`js/main.js`）がRECONのDBを直接読む案も不採用。アプリ側がDBのバージョンを上げるとき本体の接続が更新を妨げる（versionchangeのブロック）うえ、RECONを一度も開いていない状態で本体が`indexedDB.open`すると、空のDBを作ってしまうため。

## データ構造（DB `sideops_recon`、バージョン1）

| ストア | キー | 内容 |
|---|---|---|
| `transactions` | `id` | 取引1件＝1レコード。索引：`importId`・`ptx`（販路＋取引ID）・`ym`（年月） |
| `imports` | `id` | 取込1回＝1レコード（取消の単位）。索引：`fileHash` |
| `readers` | `id` | 読者（段階3bで使用。器だけ先に作成） |
| `works` | `id` | 作品のまとめ（表記違いを1つにした作品）：`{ id: 'w_…', brand, name（表示名）, createdAt, updatedAt }`。まとめていない作品はレコードを持たない |
| `aliases` | `id` | 表記・IDの対応表。読者・作品レコードの中の配列ではなく独立したストアにする。将来Flutter版（SQLite）へ移すとき、表の形のまま移せるため。作品：`{ id: '["work",ブランドID,作品名キー]', type: 'work', brand, key（NFKC正規化した作品名）, workId, createdAt }` |
| `profiles` | `id` | 取込プロファイル。段階1はnote用（`id: 'note'`）の「決済種別の扱い」だけを持つ |
| `settings` | `key` | `brands`（ブランド一覧）・`ui`（伏せ字のON/OFF）・`workSuggestIgnore`（「別の作品」とした候補の組）・`backup`（`lastExportAt`：最後にバックアップを書き出した日時） |

7ストアを最初から作っておくのは、後の段階でDBのバージョンを上げる回数を減らすため（索引の追加は段階3でバージョン2に上げて行う想定）。

### transactions（取引）

```js
{
  id: '["note","b_xxxx","TX0801A","決済"]', // 主キー：[販路, ブランドID, 取引ID, 決済種別(正規化)] をJSON化
  platform: 'note', brand: 'b_xxxx', ptx: 'note|TX0801A',
  txId: 'TX0801A', kindKey: '決済', kindText: '決済',
  kind: 'sale',                  // 'sale'（売上）| 'refund'（返金）| 'ignore'（集計しない）
  paidAt: '2026-08-01T10:15:30+09:00', date: '2026-08-01', ym: '2026-08',
  buyerName: '（CSVのまま）', buyerKey: '（NFKC正規化）',
  buyerStatus: 'unmatched',      // 下記「購入者の状態」
  readerId: null,                // 段階3（名寄せ）で埋める
  contentName: '（CSVのまま）', contentKey: '（NFKC正規化）', contentType: '記事',
  workId: null,                  // 段階3で埋める
  payMethod: 'クレジットカード', currency: 'JPY', quantity: 1,
  priceRaw: 300,                 // CSVの販売額（符号込み）
  amount: 300,                   // 差引への寄与額（下記の規則で計算）
  priceExTax, tax, taxRate, points, issuer, issuerRegNo,
  importId: 'imp_20260930042400_ab12', rowNo: 1,
  raw: { '決済/返金日時': '…', … }, // 元の行（見出し→値）。後から検証・再計算できるように丸ごと残す
  createdAt: 1790000000000
}
```

- **主キーに決済種別を含める理由**：返金の行が、元の売上と同じ取引IDを持つ可能性があるため（要確認事項）。含めないと、返金が「取込済みの重複」と誤判定されて消え、売上が過大になる
- **差引への寄与額（`amount`）**：売上＝販売額そのまま（符号込み）／返金＝販売額の**絶対値を引く**／集計しない＝0。CSVが返金をマイナスで書く場合もプラスで書く場合も、同じ結果になる
- `priceRaw`と`raw`を残しているので、決済種別の扱いを後から変えても再計算できる（再適用の機能は段階3以降）
- 日時は日本時間の文字列から年・月・日を直接切り出す（UTCに変換しない）。月末深夜の取引が翌月・前月にずれない

### 購入者の状態（`buyerStatus`）

| 値 | 意味 |
|---|---|
| `matched` | 照合済み（段階3で読者に紐付いた） |
| `unmatched` | 未照合（名寄せ待ち）。段階1で取り込んだ個人名はすべてこれ |
| `unidentifiable` | 識別不能：「ゲスト」「退会したユーザー」などの共通表記と空欄。同じ表記でも別人の可能性が高いため、名寄せの自動照合に使わない |
| `anonymous` | 匿名：販路がそもそも購入者情報を出さない（段階4の汎用取込で使用） |

共通表記の一覧は`recon.js`の`GENERIC_BUYER_NAMES`（NFKC正規化・大文字小文字を無視して完全一致）。

### imports（取込の履歴）

ファイル名・サイズ・SHA-256・文字コード・ブランド・期間（読み取れた行の最初と最後の日付）・件数（行数／追加／スキップ／除外）・追加分の合計（売上・返金・差引）・管理画面との照合（`reconcile`：`[{ ym, entered, csvSale, csvNet, result: 'net'|'sale'|'mismatch' }]`、入力した月だけ。2026-10-02以前の履歴にはない）・取込日時。

### ブランド（`settings`の`brands`）

`{ id, name, color, createdAt }`の配列。ブランドは販路をまたぐ単位（同じブランドがnoteとBOOTHで売ることもある）。**名前の重複不可・40文字まで・取引が1件でもあるブランドは削除不可**（履歴から取り消せば削除できる）。色はユーザーが選ぶアプリ固有の色なので、テーマブリッジの対象外。

## noteのCSV取込

### 対象

noteの「記事の販売履歴」CSV（ダッシュボード→販売履歴→エクスポート設定→対象年月→エクスポート）。列は次の14個で、太字の6列が必須。

**決済/返金日時**、**購入者名**、**決済種別**、決済方法、コンテンツ種別、**コンテンツ名**、**販売額**、消費税率、税抜販売額、消費税額、ポイント利用、**取引ID**、発行事業者、適格事業者登録番号

### 読み取りの規則

| 項目 | 規則 |
|---|---|
| 見出し行 | 先頭10行から、必須列がすべてそろう行を探す（見出しの上に説明行があっても読める）。見出し名はNFKC正規化＋空白除去で照合。知らない列は「お知らせ」に出して取込には使わない |
| 文字コード | BOM（UTF-16LE）→ UTF-8（厳密に判定）→ 失敗したらShift_JIS。確認画面で手動でも切り替えられる |
| 区切り | Papa Parseの自動判定（カンマ・タブ・セミコロン）。引用符内のカンマ・改行・`""`も正しく読む |
| 日時 | **実際のnoteのCSVは`20251113205937`（年月日時分秒の14桁、区切りなし）**（2026-10-02に実データで判明）。ほかに12桁（秒なし）・8桁（日付のみ）、`2026/08/01 10:15:30`・`2026-08-15 9:05`・`2026年8月1日`・全角数字なども受け付ける。存在しない日付（2月30日など）はエラー。Excelで開くと14桁の数字が`2.02511E+13`のような指数表記に崩れるため、その場合は専用の文言で知らせる |
| 金額 | `¥`・カンマ・`円`・全角数字・マイナス記号の揺れ・会計の`▲`/`△`・括弧表記を吸収。販売額が整数でなければエラー |
| 名前・作品名 | 保存はCSVのまま。照合用のキーはNFKC正規化（全角英数・半角カナ・全角スペースの揺れを吸収） |

### 確認画面と検算

取り込む前に必ず確認画面を出す。確定ボタンは、次がすべてそろうまで押せない（押せない理由は検算欄の下に一覧で出る）。

- ブランドを選んだ（**自動では選ばない**。発行事業者の値は目視確認用に表示するだけ）
- すべての決済種別に扱い（売上として加算／返金として減算／集計しない）を選んだ（**初めて出てきた値は既定値で黙って決めず、必ず人が選ぶ**。選んだ扱いは`profiles`に保存し、次回から自動で使う）
- 読み取れない行がある場合、除外に同意した
- 別ブランドで取込済みの取引IDがある場合、確認のチェックを入れた
- 新しく追加される取引が1件以上ある

**検算欄**は、このファイル全体の「売上・返金・差引」（noteの管理画面の数字と見比べる用）と、新規／取込済みでスキップ／読み取れず除外／集計しない の件数、「今回増える差引」を表示する。合計の下には帳簿の作法どおり二重線を引く。

### 管理画面との照合（2026-10-02追加）

目視の検算を機械に任せるため、検算欄に「管理画面と照合」（任意）を置く。

- CSVに含まれる月ごとに入力欄を出す。noteの管理画面に出ている月の合計（税込）を入れると、その月の**ファイル全体**（取込済みでスキップする行も含む。読み取れずに除外した行は含まない）の**差引か売上のどちらか**と一致すれば「一致（差引／売上）」と表示する。管理画面の数字がどちらに当たるかを決め打ちしないため（実データで確かめたら片方に絞ってよい）
- 不一致なら、CSVの差引・売上と「差引との差」を出し、**「一致しない理由を確かめた」のチェックを入れるまで確定できない**。除外した行があれば「それが原因かもしれない」と添える。金額を書き換えるとチェックはやり直し
- 数字として読めない入力（`abc`等）は確定不可（空欄に戻せば解除）。決済種別の扱いが未設定の間は照合しない
- 空欄なら照合しない（確定の条件にもならない）
- 結果は取込の履歴（`imports`の`reconcile`）に入力した月だけ残し、履歴の行に「管理画面と一致」「管理画面と不一致 ○月」の印を出す（印にマウスを載せると金額の内訳）
- 入力欄は、ファイルか月の並びが変わったときだけ作り直す（入力のたびに作り直すと、フォーカスと入力中の文字が消える）。文字コードを切り替えても入力値は引き継ぐ

### 重複防止（三重）

1. **ファイル単位**：SHA-256が同じファイルは取り込めない（取り消せば再び取り込める）
2. **取引単位**：主キーが同じ取引は「取込済み」としてスキップ。期間が重なるCSV（8月分と8〜9月分など）を続けて取り込んでも二重にならない
3. **書き込み時**：`add`で書き込むため、別のタブなどで先に同じ取引が入っていれば取込全体が中止される（下記）

### 確定（1トランザクション）

取引・取込の履歴・決済種別の扱いを**1つのトランザクションで**書く。1件でも失敗すれば全体が取り消され、「一部だけ保存された」状態は起きない（`IndexedDB実装パターン_仕様書.md`の「一括取込の型」）。

### 取消

取込の履歴から1回分ずつ取り消せる（その回に追加した取引と履歴を、1つのトランザクションで削除）。確認ダイアログに件数と差引を出す。決済種別の扱い（設定）は取り消しても残る。

## 作品別売上（2026-10-02追加。ユーザーの提案）

- **作品の単位**：ブランド＋作品名（NFKC正規化）の完全一致。全角・半角の揺れはこれで吸収される。それ以外の表記違いは**自動ではまとめない**（間違ってまとめると集計が黙って狂うため、人が判断する。`note連携_仕様書.md`の「完全一致のみ・外れたら人が判断」の方針）
- **ランキング**：絞り込みはブランド・期間（全期間／年／月。取引のある年と月だけを出す）。並べ方は「売上額の順」（差引）と「件数の順」（売上の件数）。表示は TOP 10／20／50／すべて。**同じ値は同じ順位**（1, 2, 2, 4…）で、TOP n の境目で同じ順位が続く場合はその順位まで全部出す。上位3つは強調し、横棒で1位との比を示す。「集計しない」種別の取引は含めない
- **作品から取引履歴へ**：作品名を押すと、その作品（まとめた表記も含む）で絞り込んだ取引履歴を開く。期間が月なら月の絞り込みも引き継ぐ。絞り込み中は帯で示し、「作品の絞り込みを解除」で戻る。月別売上から月を開いたときは作品の絞り込みを外す
- **表記違いの候補**：空白・記号・句読点を除いて小文字にそろえると同じになる作品名（同じブランド内）を「表記違いかもしれない作品名」として示す（【】や「」の中の文字は残すので、「【前編】」と「【後編】」のような別作品は候補にならない）。「まとめる」でまとめる画面へ、「別の作品」で候補から外す（外した組は`settings`の`workSuggestIgnore`に覚え、再び出さない）
- **手でまとめる**：各行のチェックで2つ以上選び「選んだ作品をまとめる」。別のブランドの作品はまとめられない（作品は1つのブランドに属する）。まとめる画面では、売上件数の最も多い表記を既定の表示名にし、他の表記を選ぶか自由に入力もできる（入力した名前は空白だけ整え、全角記号などは入力どおり残す。200文字まで）。すでにまとめた作品を含めてまとめた場合は、その作品に吸収する
- **まとめの保存**：`aliases`（表記→作品）と`works`（表示名）に1トランザクションで書く。**取引のデータは書き換えない**（`transactions.workId`は使わず、表示のたびに`aliases`から引く）。解除すれば元どおり
- **まとめの確認・変更・解除**：「N表記をまとめ済み」の印を押すと、まとめている表記（取引のない表記も「取引なし」で表示）を一覧し、表示名の変更とまとめの解除（確認ダイアログあり）ができる
- 取込を取り消して取引がなくなった作品は一覧から消える（まとめの情報は残るので、取り込み直せば元のまとめで集計される）

## バックアップ（2026-10-02追加）

作品のまとめ（今後は顧客の名寄せ・note ID）は人の手作業で、**元のCSVから作り直せない**。そのため段階3aでJSONバックアップを入れた（MANUSCRIPTと同じ型）。

- **書き出し**：☰「バックアップを書き出す」。7ストアすべてを1つのJSON（`{ format: 'sideops-recon-backup', version: 1, dbVersion, exportedAt, stores }`）にして`recon-backup-YYYYMMDD-HHMM.json`で保存。**購入者名を含むので公開の場所に置かない**よう、書き出し後に知らせる
- **バックアップ忘れの印**：手作業のデータ（作品のまとめ）があるときだけ、最後の書き出しから7日以上で☰に琥珀色の印を付け、メニューに経過日数を出す（一度も書き出していなければ「まだ書き出していません」）。手作業のデータがなければ、すべてCSVから作り直せるので印は付けない
- **復元**：☰「バックアップから復元」。形式（`format`・`version`）と各ストアの中身（キーの有無、取引の金額・年月・ブランド）を確かめ、合わなければ何もしない。確認ダイアログに「今のデータ」と「バックアップの内容」の件数を並べ、**全部を置き換える**（混ぜない）。1トランザクションで全ストアを消して書き込み、途中で失敗すれば何も変わらない。開いている取込の確認画面は閉じる

**スマホ（幅640px以下）**：取引の1行を2段（1段目：作品名と金額／2段目：日時・ブランド・購入者と種別）に組み替える（`.tx-sub`をPCでは`display: contents`、スマホでは横並びにする）。確認画面は1列にし、検算欄は最後に置く。

## フールプルーフ一覧

| 対象 | 対策 |
|---|---|
| ファイル選択 | 拡張子（.csv/.tsv/.txt）・10MB上限・空ファイルを拒否。複数ドロップは先頭のみ読み込んで知らせる |
| ドロップの取りこぼし | 枠の外にファイルを落としても、iframeの画面がファイル表示に置き換わらない（window全体で既定動作を止める） |
| 形式違い | 必須列がそろわなければ取り込めない。見つからない列名と「文字コードの切替」を案内 |
| 文字化け | 文字コードを自動判定し、確認画面で切り替え可能 |
| 読み取れない行 | 合計行・区切りの崩れ・引用符の崩れ・空の取引ID/作品名・読めない日時/金額・整数でない金額を行番号つきで表示。除外への同意がないと確定不可 |
| Excelで壊れたCSV | 取引ID・日時が`1.2E+11`・`2.02511E+13`のような指数表記に崩れていたらエラー（Excelで開いて上書き保存すると起きる。noteから書き出し直すよう案内） |
| 管理画面との食い違い | 照合欄に入れた金額が差引・売上のどちらとも合わなければ、確認チェックまで確定不可。金額を変えたらチェックはやり直し |
| ファイル内の重複 | 同じ取引ID・種別の行が2つあればエラー（黙ってどちらかを捨てない） |
| ブランドの選び間違い | 自動選択しない。別ブランドで取込済みの取引IDがあれば警告し、確認チェックが必須。ブランドを選び直すとチェックはやり直し |
| 返金など | 取込済みの取引と取引IDが同じで種別が違う行は「お知らせ」で知らせ、別の取引として追加 |
| ブランド混在 | 1ファイルに発行事業者が複数あれば「お知らせ」で知らせる |
| 未知の決済種別 | 「初めての値」の印を付け、扱いを選ぶまで確定不可 |
| 二重押し | 確定処理中はボタンを無効化 |
| 書き込みの途中失敗 | 1トランザクション＋`add`。途中で例外が出たら明示的に`abort`し、何も保存しない |
| 同じファイル | SHA-256で検知し、取込日時とファイル名を示して止める |
| ブランド名 | 空・40文字超・同名（NFKC・大文字小文字を無視）を拒否。取引のあるブランドは削除不可 |
| 保存できない環境 | IndexedDBが使えない（`file://`・プライベートモード等）場合、理由を画面に表示 |
| 別タブでのDB更新 | `onversionchange`で接続を閉じ、再読み込みを促す |
| ブラウザによる消去 | 起動時に`navigator.storage.persist()`を要求。☰「保存領域の状態」で状態・使用量を確認でき、手動でも要求できる |
| 作品の誤ったまとめ | 自動ではまとめない（候補を示すだけ）。別ブランドの作品はまとめられない。取引は書き換えないので、解除すれば元どおり |
| 表記違いの候補の出しすぎ | 「別の作品」とした組は覚えて、再び出さない |
| 手作業のデータの消失 | JSONバックアップ。手作業のデータがあり、最後の書き出しから7日以上なら☰に印 |
| 復元の取り違え | 形式・中身を確かめてから、今とバックアップの件数を並べた確認ダイアログ。1トランザクションで置き換え、失敗すれば何も変わらない |
| スマホでの伏せ字の見落とし | 伏せ字ボタンを☰に移した幅では、伏せ字の間☰を琥珀色にする |

## セキュリティ・個人情報

- **CSP**：`default-src 'none'; script-src 'self'; style-src 'self' 'unsafe-inline' https://fonts.googleapis.com; font-src https://fonts.gstatic.com; img-src 'self' data:; connect-src 'none'; form-action 'none'; base-uri 'none'`。外部への送信経路（fetch・フォーム送信など）を塞ぎ、インラインのスクリプトも禁止（JSはすべて外部ファイル）。許可しているのは同じサイト内のファイルとGoogle Fontsだけ
  - **検証時の注意**：CSPで文字列の`eval`が禁止されているため、Playwrightの`page.wait_for_function`は拒否される。待ち合わせは`expect(locator).to_have_count()`等のロケーターで行う
- **伏せ字モード**（スクリーンショット用）：購入者名を「購入者 XXXX」（名前から計算する4文字の記号。同じ人は同じ記号になるので、伏せたままでも見分けられる）に、発行事業者を「●●●」にする。「ゲスト」等の共通表記は個人を指さないのでそのまま。ON/OFFは保存される
- **実データの置き場所**：販売CSV・バックアップは公開リポジトリに置かない（テストはダミーCSVで行う）。元のCSVはPCの手元に保管する。取込のデータは元のCSVから作り直せるが、作品のまとめはバックアップでしか戻せない
- **インポートしたhtmlの注意**：後天的アプリ（`srcdoc`で表示）はsandbox指定がなく本体と同じオリジンで動くため、そのhtmlのJSは`sideops_recon`（顧客データ）も読めてしまう。自作以外のhtmlはインポートしない（`アプリランチャー_仕様書.md`）
- **端末ごとのデータ**：IndexedDBはブラウザごと・端末ごとに別。取込はPCで行う運用を基本にする

### 2026-10-02 実データ（1ブランド・1か月分・4行、返金なし）で確定したこと

- **列**：14列の見出しがこの仕様のとおりにそろっていた（「見慣れない列」のお知らせなし）。文字コードはUTF-8と判定され、文字化けなし
- **日時**：`20251113205937`（14桁・区切りなし）。最初は全行が「日時を読み取れません」になったため対応した
- **決済種別**：売上の行は**「販売」**（ダミーCSVで仮定していた「決済」ではなかった）。初めての値として扱いを選ぶ欄が出ることを確認
- **購入者名**：noteの表示名。購入者を出さない購入は「ゲスト」（4行中2行）で、識別不能（共通表記）として扱われることを確認。表示名なので改名で揺れうる前提は変えない（名寄せは段階3）

- **管理画面との照合**：管理画面の月の合計を入れて「一致」になることをユーザーが確認
- **返金**：ユーザーの見立てでは、返金はCSVに載らないらしい（確証はない）。**決済種別まわりの仕様は現状のままで確定**（ユーザー判断）。返金の扱い（減算・主キーに種別を含める設計）は、載ってきた場合の備えとしてそのまま残す。返金の行が現れたら「初めての値」として必ず人が扱いを選ぶので、黙って誤集計はしない

### まだ確認できていないこと（急がない）

- 「販売」以外の決済種別（サポート・メンバーシップ・返金など）。出てきたら確認画面で扱いを選ぶだけでよい
- コンテンツ種別の実際の値（記事・マガジン・メンバーシップなど。確認画面には出していない）
- 管理画面の月の合計がCSVの差引と売上のどちらに当たるか（返金がCSVに載らないなら常に同じ値で、区別は不要）
