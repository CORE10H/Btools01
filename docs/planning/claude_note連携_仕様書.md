# note連携・INTELパネル拡張の設計方針 仕様書

**この文書は設計方針の記録であり、実装（拡張機能のコード・INTELパネルの内部データ構造）はまだ着手していない。**

## スコープの線引き（重要な前提）

- **対象は「公開領域」のみ**：フォロワー数（プロフィールページ）、記事ごとのスキ数・スキした人一覧（記事ページ）。これらはログイン不要で誰でも閲覧できる公開情報
- 「高評価」機能（note公式が2024年7月に有料記事向けに正式リリースした独立機能）はスキとは別物で、対象データから外す
- **ダッシュボード（PV数・売上等の非公開領域）は対象外**：拡張機能が機械的にその中身を読み取り外部保存する行為は、note社との関係（規約解釈・アカウント停止リスク）の観点で避ける。売上データは別途CSVエクスポートで取り込む
- **配布物には一切含めない**：この拡張機能はSIDE-OPS本体（配布前提）とは完全に切り離した、個人専用の別成果物

## 採用手段：ブラウザ拡張機能でのDOM読み取り

実際にブラウザで開いたページの中身を、拡張機能が読み取るだけの方式。note社サーバーへの新規アクセスを一切発生させない（人間の通常閲覧と外形的に区別がつかない）ため、非公式APIの直接呼び出しやIFTTT経由のポーリングと比べてリスクが低いと判断し採用。

## 拡張機能の技術構成（案）

- **対象ブラウザ**：Edge（Chromium系）。Manifest V3で作成すれば、Chrome等の他Chromium系ブラウザにもほぼそのまま流用可能
- **発火条件**：「note.comを開いたら常時発火」（SIDE-OPS経由に限定しない簡略版）
- **発火の仕組み**：`manifest.json`の`content_scripts`で対象を`note.com`のみに限定。`location.pathname`で「プロフィールページか」「記事ページか」を判定し、それぞれ違う抽出処理を実行
- **保存先**：`chrome.storage.local`を想定。SIDE-OPS側への具体的な受け渡し方式（`chrome.runtime`経由の中継等）は未設計
- **note記事の一意キー**：URLに含まれる`n`から始まる記事ID（例：`n4f0c7b884789`）。編集・タイトル変更をしても記事が存在する限り不変

## 対象データ（最終確定）

- フォロワー数（プロフィールページから取得。1万人未満のみ正確な数値、以上は「1.0万」等の概算表示になるnote仕様上の制約あり）
- 記事ごとのスキ数（記事ページから取得。省略なしの正確な数値）
- 記事ごとの「スキした人」一覧（記事ページから取得）

高評価数・コメント数・ダッシュボード系（PV・売上）は対象外。

## 通知パネル（LOG）への反映仕様（スキの増加通知）

- **検知**：前回保存値と今回取得値を比較し、スキ数の増加を検知
- **表示単位は「日」**：同じ日のうちに複数回増加を検知しても、その日の通知は1件のまま、増加数（n）だけ更新する。表示位置（順番）は変えず、nの部分だけ強調表示
- **日付の切り替え**：日本時間0:00をまたいだら前日分の通知を確定・固定し、新しい日の通知を別途追加。「前回より」の基準点は、前日最後に確定した値
- **文言**：「〇〇の記事のスキが前回よりn件増加しています」

## INTELパネルの内部データ構造（→ RECONへ移管）

> **【2026-09-30 更新】この内部データの正本は、INTELパネルではなく販売データの取込・分析アプリ「RECON」（`apps/recon.html`、DB`sideops_recon`）が持つことに決定した。** INTELパネルはRECONの段階2で「集計済みの要約」だけを受け取って表示する（理由は`アプリ_RECON_仕様書.md`の「データの持ち場所」）。以下の「3層構造」「完全一致のみ・外れたら隔離して人が判断」の考え方はRECONに引き継いでいる。RECONで変えた点：
> - ブランドの軸を追加（1取引＝販路×ブランド。顧客IDはブランドをまたいで1人に1つ）
> - `includeInSales`（含める／除外の2択）を、決済種別ごとの3択（売上として加算／返金として減算／集計しない）に変更。返金は符号に関係なく絶対値を引く
> - 照合の前にNFKC正規化（全角英数・半角カナ・全角スペースの揺れを吸収）
> - 購入者の状態を4種に（照合済み／未照合／識別不能＝「ゲスト」等の共通表記・空欄／匿名＝販路が購入者を出さない）
> - 表記・IDの対応表（`platformNames`・`knownTitles`・`platformIds`にあたるもの）は、配列ではなく独立したストア`aliases`に置く
> - 通貨・数量・税抜額も最初から保持する
>
> **現在のデータ構造・取込仕様は`アプリ_RECON_仕様書.md`が正。** 以下は設計当時の記録として残す。

INTELパネルは「外側（画面表示）」と「内側（内部で持つデータ）」を分けて考える。**外側の表示面（売上・稼働時間・コスト・純利益の4枠）は変更しない。** 内側のデータストアを、note連携も含めた実績系データ全般の一元的な置き場所として設計する。

### 最重要コンセプト：「3層構造」で考える

同じ人物・同じ作品でも、note・BOOTH・Kindleのように将来複数のプラットフォームを扱うようになると、プラットフォームごとにIDの体系も識別できる情報の粒度も異なり、さらに同一プラットフォーム内でも表記の揺らぎ（改名等）が起こる。この問題に対処するため、データを3層に分けて考える。

```
層1：SIDE-OPS内部の"実体"（プラットフォームを問わない、本物の人・本物の作品）
　→ readers[].id / works[].id が該当
　↑ ひもづく（プラットフォームごとの対応表）
層2：プラットフォームごとの"顔"（例：note上では「たろむ」「たろこ」）
　→ readers[].platformNames / works[].platformIds が該当
　↑ ひもづく（完全一致で突合、外れたら人間が判断）
層3：生データ（CSVの1行、拡張機能が読み取った1件）
　→ transactions（取引）、拡張機能が検知したスキ・フォロワー数の生の値 が該当
```

新しい生データ（層3）が来るたびに、層2の対応表と完全一致で突合する。一致すれば自動処理、一致しなければ「隔離」して確認を仰ぎ、確認後に層2の対応表を更新する。この「完全一致のみ・外れたら人間の判断」というルールは、読者の名寄せにも、作品の名寄せにも、プラットフォームが増えても、すべて同じ考え方を適用する。

### 内部データの大項目（業務領域ごと）

```
sales, costs, workHours  … 売上・コスト・稼働時間管理。箱の存在のみ決定、中身は未設計
transactions              … 取引（購入）の生データ。CSVインポート由来。「唯一の正」
readers                   … 読者管理（人物単位）。「行動（スキ・購入）した人だけ」を記録する方針
works                     … 作品管理（記事単位）
followerLog               … フォロワー数。単純な数値推移のみ、人物データは持たない
```

**読者管理の設計思想**：「フォロワー」は数だけ追い、個人単位のデータとしては持たない（実質的な関係のないフォロワーが多く含まれノイズが増えるため）。実際にスキ・購入といった行動を起こした人だけを読者として記録する。

**顧客（購入者）とフォロワーの違い**：「顧客」は「お金を落としてくれた人」を指す狭い言葉として運用する。フォロワーは「まだ何も買っていないかもしれない人」を含むため、別カテゴリとして扱う。

### readers（読者管理）のデータ構造

```js
readers: [
  {
    id: "person_001",                       // SIDE-OPS内部の一意ID（層1の実体）
    displayName: "たろう",                   // SIDE-OPS上の管理名
    platformNames: [                        // 層2：プラットフォームごとの"顔"（揺らぎ吸収用の配列）
      { platform: "note", name: "たろむ" },
      { platform: "note", name: "たろこ" },
    ],
    likedWorks: [                           // スキした記事一覧（拡張機能から）
      { workId: "work_001", firstLikedAt: 1732000000000 }
    ],
    createdAt: 1732000000000,
    // purchases・totalSpent は持たない。売上情報は transactions から都度集計する
  }
]
```

名寄せの自動判定は完全一致のみ（曖昧な類似判定は行わない）。

```
新しい表示名を検知（拡張機能のスキ検知、またはCSVインポートの購入者名）
  ↓
既存の全読者の platformNames 配列を完全一致で検索
  ├─ 一致した → 自動でその読者に追加（確認なし）
  └─ 一致しなかった → 「『〇〇』が見つかりません。新規追加しますか、既存の読者に組み入れますか？」と確認
       ├─ 新規追加 → 新しい読者として登録し、platformNames に今回の名前を追加
       └─ 既存に組み入れ → リストから選んで、その読者の platformNames 配列に追加
```

「実は同一人物だった」場合に統合する手動マージ機能は未設計（持ち越し）。

### transactions（取引）のデータ構造 ― 売上データの「唯一の正」

読者の購入履歴・金額（`readers`側）や作品の売上集計（`works`側）を、それぞれのレコードに個別に持たせる設計は「二重管理で矛盾が起きる」という理由で却下した。取引（購入）の実体は`transactions`という独立したデータの塊にのみ持たせ、`readers`・`works`はどちらもそこへの参照（`readerId` / `workId`）だけを持つ。集計が必要なときは都度`transactions`を検索・合算する（再計算方式。CSVの再取込やデータ修正があっても矛盾が起きにくい）。

```js
transactions: [
  {
    transactionId: "取引ID",              // CSVの「取引ID」列。プラットフォーム内では一意
    platform: "note",                     // 層2：将来 "BOOTH" 等が入る拡張ポイント
    paidAt: "決済/返金日時",
    buyerName: "購入者名",                 // CSVそのまま（生データ、層3）
    readerId: "person_001",               // 突合できた読者ID（未照合ならnull。隔離対象）
    contentName: "コンテンツ名",
    workId: "work_001",                   // 突合できた作品ID（未照合ならnull。隔離対象）
    amount: 500,
    paymentKind: "決済",                   // CSVの「決済種別」列。値の種類は未知数
    includeInSales: true,                 // 売上集計に含めるか
  }
]
```

重複防止のキーは`platform + transactionId`の組み合わせ。

### works（作品管理）のデータ構造

`readers`と同じ「内部の実体（層1）＋プラットフォームごとの顔（層2）」の二層構造を適用する。同じ作品を複数プラットフォームで販売する場合も、1つの`works`レコードとして扱う。

```js
works: [
  {
    id: "work_001",                        // SIDE-OPS内部の一意ID（層1の実体、プラットフォーム非依存）
    displayTitle: "母と息子「潮騒の詩」最終話",
    knownTitles: ["母と息子「潮騒の詩」最終話"], // 層2：CSV等で見つかったタイトル表記の揺らぎ吸収用配列
    platformIds: [                          // 層2：各プラットフォームでのID・URL・固有指標
      {
        platform: "note",
        id: "n4f0c7b884789",                // note記事ID（URLのnから始まる文字列。不変）
        url: "https://note.com/...",
        isPaid: true,
        metrics: { likes: 19 }
      }
    ],
    firstSeenAt: 1732000000000,
    lastCapturedAt: 1732000000000,
    // salesCount・salesAmount は持たない。売上は transactions を workId で検索して都度集計する
  }
]
```

note記事IDは記事の一意キーとして安定している（URLの`n`から始まる文字列。編集・タイトル変更をしても記事が存在する限り不変）。CSVにはコンテンツ名（タイトル文字列）しかなく記事IDが無いため、CSVインポート時は`knownTitles`配列との完全一致でしか突合できない。

### CSVインポート（note「記事の販売履歴」エクスポート）の仕様

**取得元**：noteダッシュボード→販売履歴→エクスポート設定→対象年月を選択→販売履歴のエクスポート。書き出し完了はメール通知、7日間・何度でも再ダウンロード可能。

**CSVの列構成**：

```
決済/返金日時, 購入者名, 決済種別, 決済方法, コンテンツ種別, コンテンツ名,
販売額, 消費税率, 税抜販売額, 消費税額, ポイント利用, 取引ID, 発行事業者, 適格事業者登録番号
```

**「決済種別」列の扱い（要注意・知見不足の項目）**：これが取引種類（決済／返金）を指すのか、支払い手段を指すのか、現時点で知見が無い。安全側に倒した設計として：

1. CSVを読み込んだら、まず`決済種別`列に実際に登場した値の種類と件数を集計して一覧表示する（例：「決済: 45件」「返金: 2件」）
2. 値の種類ごとに「売上に含める／除外する」を選択する
3. 選択結果を`transactions[].includeInSales`に反映する。除外された行もデータ自体は消さず保持する

**購入者名・コンテンツ名の突合フロー（統一版）**：

```
CSVの1行を読み込む
  ↓
【購入者名】既存読者の platformNames（platform: "note"）配列と完全一致するか確認
  ├─ 一致 → readerId を確定
  └─ 不一致 → readerId は null のまま「隔離」

【コンテンツ名】既存作品の knownTitles 配列と完全一致するか確認
  ├─ 一致 → workId を確定
  └─ 不一致 → workId は null のまま「隔離」

readerId・workId のどちらか一方でも null の取引 → 「未照合の取引」として一覧に表示し、確認を仰ぐ
  ↓
確認後の選択：
  購入者名について → 既存読者の platformNames に追加 or 新規読者として登録
  コンテンツ名について → 既存作品の knownTitles に追加 or 新規作品として登録
  ↓
確定したら該当の transactions レコードの readerId / workId を埋める
```

この「隔離して人間に確認する」仕組みは、CSVインポートに限らず、拡張機能側のデータ取得（読者の名寄せ）にも共通で使う設計思想。

## 未確定・持ち越しの論点

- 拡張機能側（`chrome.storage.local`）とSIDE-OPS側（IndexedDB）の具体的な受け渡し方式（content script構成、`chrome.runtime.sendMessage`の設計）はまだコードに起こしていない
- 「未照合の取引」「隔離」を実際にどんなUI（一覧画面、モーダル等）で見せるかは未設計
- 読者・作品の手動マージ機能は未設計
- INTELパネルの画面表示 → 売上枠はRECON段階2で設計済み（`アプリ_RECON_仕様書.md`）。稼働時間・コスト枠は連携元がないため「未連携」と表示する方針
- `sales` / `costs` / `workHours`ストア自体の詳細なデータ構造（箱の存在だけ決めた状態）
- noteの`決済種別`列の値の実態が依然未確認（RECONは初めての値を必ず人が扱いを選ぶ設計のため、未知の値でも黙って誤集計はしない）
- note以外のプラットフォーム（BOOTH・Kindle等）の具体的なデータ取得方法・列構成は、実際にそのプラットフォームを使うことになった時点で個別に調査・設計する（3層構造・platformIds設計により、追加時の土台は既にある）
