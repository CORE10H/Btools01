# アプリランチャー 仕様書

対象：SIDE-OPS本体のカバーフロー（縦型・cards/apps分離方式）。他アプリを起動する入口。

## 概要

- 16:9固定、iPod Cover Flow風。中央バナーが正面表示、上下のバナーは`rotateX`で奥行きを持って並ぶ
- 循環スクロール（最短経路で回り込む）。マウスホイール／▲▼ボタンで送れる
- ラベル表記は「APPS」

## データ構造（IndexedDB駆動、cards/apps分離方式）

保存先DB名：`sideops_launcher`

3層構造：

1. **①`cards`ストア**（カバーフローの見た目・並び）：カテゴリ表示・カバー画像（16:9、Blob保存）・アプリの名称（旧称オーバーレイ文字。変数名は`overlayText`のまま）・並び順・`sizeMode`（4.2節「メインステージ_仕様書」参照）
2. **②`apps`ストア**（アプリ本体の実体への参照。「どこに実体があるか」を示す参照情報の集まりであり、アプリの実体そのものは内包しない）
3. **③各アプリ専用のIndexedDB**（`sideops_memo`等）：カバーフロー機構とは完全に独立

`cards`ストアは`apps`ストアの各レコードの`id`を外部キーとして持つのみ。

### apps ストアの種別（type）

| type | 実体の持ち方 | Stageでの表示方法 | アプリ本体を消すと |
|---|---|---|---|
| `builtin`（先天的アプリ） | `apps/`配下の**ファイルパス**を参照（`src`） | `iframe.src = app.src` | 参照（入口）が消えるだけ。実ファイルはリポジトリに残る |
| `imported`（後天的アプリ） | htmlの**中身そのもの**を文字列として保存（`htmlContent`） | `iframe.srcdoc = app.htmlContent` | 保存されていた実体そのものが消える |
| `shortcut`（インターネットショートカット） | `src`にURLをそのまま保持 | `iframe.src = project.src`（URL検証あり） | 参照が消えるだけ |

- **先天的アプリ**：`BUILTIN_APP_CHOICES`にハードコードされたアプリ一覧
- **後天的アプリ**：ユーザーがインポートしたローカルhtmlファイル

### IndexedDBとの関係（誤解しやすい点）

各アプリが使うIndexedDB（`sideops_memo`等）は、htmlファイルの中身のJSコードが`indexedDB.open('DB名', ...)`と指定して初めて紐づく。ファイルパスやランチャーの`apps`ストアのレコードとは無関係。そのため：

- 同じ`apps/memo.html`を指す入口を何度作り直しても、常に同じ`sideops_memo`に接続する（旧データは失われない）
- インポートしたhtmlが、既存アプリと偶然同じDB名を内部で使っていた場合、データが混ざる可能性がある（フールプルーフとして警告文をモーダル内に常時表示。自動検知は行わず注意喚起のみ）
- インポートしたhtmlは`srcdoc`で表示され、sandbox指定がないため本体と同じオリジンで動く。つまり、そのhtmlのJSは他のアプリのDB（RECONの顧客データ`sideops_recon`を含む）を技術的には読めてしまう。**自作以外のhtmlはインポートしない**（2026-09-30追記）

## 「＋新規作成」カード

カバーフロー末尾に常設。クリックするとモーダルが開き、以下を設定して新規カードを作成する：

1. 種類（プルダウン：先天的アプリ一覧／「ローカルhtmlをインポート」／「インターネットショートカット」）
2. カテゴリ表示（任意）
3. カバー画像（16:9、任意）
4. アプリの名称（任意）

### 種類プルダウンの選択肢

- 先天的アプリ（builtin）一覧
- `IMPORT_OPTION_VALUE`：ローカルhtmlをインポート
- `SHORTCUT_OPTION_VALUE = '__shortcut__'`：インターネットショートカット

### 先天的アプリ選択時の自動入力

- **カバー画像の自動読込**：種類で先天的アプリを選ぶと、対応するデフォルト画像（`apps/img/`配下）を自動でfetch・Blob化してカバー画像欄にプレビュー表示する。blankは対象画像なし（それ以外の先天的アプリは全て画像あり）
  - **選び直しへの追従（2026-10-02修正）**：画像のないアプリ（blank）や「ローカルhtmlをインポート」に切り替えたら、自動で入れた画像を外して空に戻す（以前は直前のアプリの画像が残り、そのまま別のアプリのカードに保存されていた）。fetchは非同期なので、呼ぶたびに番号（`coverLoadSeq`）を進め、最後の選択の結果だけを使う（素早く選び直したとき、古い画像が後から届いて上書きするのを防ぐ）。モーダルを開き直したときも番号を進める。読み込みに失敗したときも空に戻す
- **アプリの名称の自動入力**：名称欄にそのアプリ名を自動入力する。カテゴリ表示は初期値の元データがないため対象外

いずれも共通のフールプルーフパターンを踏襲：**ユーザーが一度でも手で編集したら、以後は種類を選び直しても自動値で上書きしない**（カバー画像は既存の手動アップロード判定、名称は`overlayIsUserEdited`フラグで管理）。

## ローカルhtmlインポート機能

「種類」で「ローカルhtmlをインポート」を選択した場合のフロー：

1. ファイル選択欄・アプリ名入力欄が出現
2. `.html`/`.htm`ファイルを選択 → `FileReader.readAsText`で中身を文字列として読み込み
3. アプリ名は未入力ならファイル名（拡張子除く）から自動補完
4. 保存時、`apps`ストアに`{ type: 'imported', htmlContent: '...' }`として登録し、`cards`ストアにも1件追加

### フールプルーフ

- 拡張子チェック（`.html`/`.htm`以外は拒否）
- サイズ上限5MB（超過時はエラーメッセージで拒否）
- 種類未選択・インポートモードでファイル未選択のまま保存不可
- IndexedDB名の偶然の重複リスクについて、モーダル内に警告文を常時表示

## インターネットショートカット（外部サイトをStageで開く）

> **【現状】このアプリの実装コードは現在のリポジトリ（`CORE10H/Btools01`）に存在しない（2026-09-24確認）。実装時にpushされないまま消失したと考えられる。以下は仕様として再実装時に用いること。**

外部サイトのURLをそのままStageのiframeに表示するだけの、第3のカード種別。

### apps ストアでの扱い

`type: 'shortcut'`のアプリエントリとして登録。`src`にユーザー入力のURLをそのまま保持する。ショートカット名を未入力の場合は`new URL(...).hostname`で自動採番。

### フールプルーフ（二重バリデーション）

- 保存時：`SHORTCUT_URL_PATTERN = /^https?:\/\/.+/i`でhttp(s)://形式のみ許可。`javascript:`や`data:`等の危険なスキームを拒否
- Stage展開時：保存済みのURLに対しても`openStage`内で再度同じパターンを検証する二重防御。不正な値の場合はiframeを描画せず、エラーメッセージのみ`srcdoc`で表示

### 同一オリジンポリシーによる制約

このiframeはあくまで外部サイトを「表示」するだけであり、SIDE-OPS側のJavaScriptからその中身（DOM・テキスト）を読み取ることはブラウザの同一オリジンポリシーにより一切できない。DOM読み取りが必要な場合は別途ブラウザ拡張機能が必要（`note連携_仕様書.md`参照）。

## カード削除（表示情報のみ）

中央に来たカードには🗑削除ボタンが表示される。**削除されるのは①`cards`ストアの表示情報のみ**で、②アプリ本体・③アプリのデータは一切削除されない（安全重視）。

## アプリ管理画面（後天的アプリ本体の削除）

設定モーダル内の「アプリ管理」から開く専用モーダル。

- **表示対象**：`apps`ストアのうち`type === 'imported'`のみ。先天的アプリは一覧に出さず削除もできない
- **一覧の各行**：アプリ名、登録日、参照カード件数（何件のカバーフローカードがこのアプリを指しているか）

### 削除の仕様

- アプリ本体（②`apps`ストアの1件）を削除すると、**紐づくカード（①`cards`ストア）も連鎖削除される**
- ③各アプリ専用データ（IndexedDB本体）は**削除しない**（温存）。他アプリのDBへアクセスする手段自体が存在しないため、データ温存は設計上保証されている

### 削除確認ダイアログの出し分け

- 参照カード0件 → 通常の確認文言
- 参照カード1件以上 → 赤字で強調した警告文言（「アプリ本体を削除すると、カードN件も同時に削除されます」）。削除後もデータ自体は消えない旨を併記

## 中央バナーのクリック

中央のバナーをクリックすると、Stage内に`<iframe>`を生成し、カードが参照するアプリ本体を読み込む。「＋新規作成」カードをクリックした場合は、Stageは開かず新規カード作成モーダルが開く。

中央カードのクリック経路は`.cf-item`個別要素と`#cfOpenHit`（透明オーバーレイ、PC版のみ有効）の2経路があり、機能追加時は両方に同じデータを渡す必要がある（詳細は`3D変形とスタッキングコンテキスト_仕様書.md`参照）。

## 旧実装との関係

旧来の固定`projects`配列（ハードコード）は廃止済み。`js/main.js`内にコメントアウトで保存されている（新方式が安定稼働したら削除予定）。マイグレーションは行っていないため、初期状態のカードは空で、ユーザーが「＋新規作成」から手動で登録する運用。
